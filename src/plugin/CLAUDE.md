# Plugins (host side)

Loaded on demand; the root `CLAUDE.md` holds the invariants that apply everywhere. The authoring contract is `docs/plugin-authoring.md`; the worked example is `tests/fixtures/echo-plugin`.

Any other `resources.<group>` key is a **plugin group**: the host keeps the body verbatim (minus the reserved `options` key), a loaded `cdylib` validates and serves it, and `default_<group>` follows the same inference rule. Selection is `I use "<name>" <group>` and resets per scenario like the API does. Plugins come from a layered `.bddkit/` chain — shared, user, project directories, each read as `plugins.yaml` then `plugins.local.yaml`, a later entry overriding an earlier one of the same plugin `name` (`dirs.rs`, `plugin/lock.rs`) — or from a single `--bddkit-dir`/`BDDKIT_DIR` directory that replaces the whole chain; by default this is machine state, never committed with the suite (`plugins.local.yaml` is meant to be gitignored), except a deliberate `bddkit plugin install --layer project` (or `project.local`), which vendors `.bddkit/plugins/` into the repository on purpose. The whole authoring contract is `docs/plugin-authoring.md` and the worked example is `tests/fixtures/echo-plugin`.

## Gotchas

- **Only JSON strings cross the plugin boundary — never a Rust type, never a borrowed slice.** `rustc` has no stable ABI: a `&str` or a `Vec<T>` handed to a `cdylib` built by another compiler is undefined behaviour with no diagnostic. The contract is `*mut c_char` plus the schema in `docs/plugin-authoring.md`. Adding a "just one small struct" fast path is how that becomes a heisenbug in someone else's CI.
- **`Library`'s field order is load-bearing.** Rust drops fields in declaration order, and every function pointer in the struct points into `_library`'s mapping. `_library` is declared LAST so it is unloaded last; moving it up frees the mapping while the pointers beside it are still live. The leading underscore is the whole documentation of the field: it is never read, it exists to be dropped last.
- **A plugin instance handle is a `u64`, not a pointer.** It indexes the plugin's own table, so it is `Send + Sync` for free and can never dangle into a use-after-free on the host side — a stale or forged handle is data the plugin answers `{"status":"fatal","error":"unknown handle"}` to. The mutexes in `Plugins` protect its maps, not the handle. Do not "optimise" it back into an opaque pointer.
- **A plugin's `secret_groups` becomes synthetic `Param`s (and `ABI_VERSION` is 3: generation 2 was one bump for the request hint, `secrets`, `media_type` and `secret_groups` together, generation 3 one bump for `vars`, `wants_vars`/`raw_docstring` and `bddkit_validate_step`).** `expression::plugin_params` builds one `text`/`secret` `Param` per capture group up to the last secret one (1-based in the manifest, `args[n - 1]` in the host), so `runner::prepare`, `Registry::display_text` and `step_started.vars` treat a plugin's secret group exactly as a builtin's `{name:secret}` with no second code path; nothing is type-checked. A reply's `secrets` are registered via `Redactor::secret` (so `privacy.min_length` applies) on EVERY status, before the vars or the diagnostics are read (`a_declared_media_type_replaces_the_guess_and_declared_secrets_are_masked` goes red if the loop moves later); a fatal error is masked by the run_file final pass either way. The request's `evidence` key is `Trace::evidence_on()`, sent on every polling attempt. Plugin files stay unfiltered by design (spec section 10); a plugin built for any generation but 3 is refused at load (the check is strict, so every bump means every published plugin is re-released and the registry index gains an entry for the new number before a host can install anything), and `tests/` isolates nothing from a user-layer plugin, so run them with `XDG_CONFIG_HOME`/`XDG_DATA_HOME` pointed at an empty directory on a machine that has installed plugins.
- **A plugin step can ask for the file's variables, an uninterpolated doc string and a pre-run check; each is an opt-in, and ABI 3 moved once for the three.** `StepSpec.wants_vars` makes the runner put `vars` in the dispatch request (`plugin::request_vars`: `VarStack::visible` plus a `secret` flag per variable from `Redactor::reveals(name, value, vars.is_secret(name))` — a privacy word in the name, a value already in the set, or a `{x:secret}` macro parameter, which matters because a short secret never joins the set; `<<null>>` goes out as JSON `null`, never as the sentinel's NUL bytes). It is recomputed on every polling attempt on purpose, because a `not_yet` reply's `secrets` can change a flag, and nothing ever prints or emits it: the request is not an event, an evidence record or debug output, so a new place that logs the request would leak every secret variable. `StepSpec.raw_docstring` is read in `runner::resolve` through `Registry::plugin_step` and skips only the doc string's interpolation in `prepare` — matching still needs no value (invariant 1); the doc string reaches the plugin dedented, WITH a leading and a trailing newline (gherkin keeps them), which a plugin must count in its line numbers. `bddkit_validate_step(step_index, request)` is an optional symbol (absent means accepted; a hook that panics, returns nothing or a malformed reply is an ERROR, never acceptance) called with the RAW captures, doc string and table through ONE function, `validate::check_plugin_step`, from `validate::check`, include bodies and the `Plugin` arm of `Registry::validate_macros` — which is why `with_macros_and_plugins` takes the plugin handle: macros are validated while the registry is built. Its error text passes only the process-wide sink, not the file's secret set, so a plugin must not quote a `secret_groups` argument in it. A file included from a macro body is not walked, so a plugin step there gets no `validate_step`; a macro-body rejection is the first error of the registry build, hence exit 2 in `run` and the `macros` row (the steps stage skipped) in `doctor`.
- **Plugin steps never become `StepId` variants.** They are `StepTarget::Plugin { lib, step, assertion }` — indices into `Plugins::steps()` — resolved at run time from `list_steps`, so invariant 4 (exhaustive dispatch, no catch-all) is untouched by them. The one plugin-related `StepId` is `UsePluginInstance`, the group-switch built-in.
- **`I use "<name>" <group>` is BUILT at startup from the loaded group names**, as `^I use "(?P<name>[^"]*)" (?P<group>g1|g2)$` in `Registry::add_use_group_step`. It is not a static entry in `BUILTIN_STEPS`, because `regex` has no lookahead and so cannot express "any word except api/connection" — an alternation over the real names is the only way it cannot overlap `I use "<name>" api` or `I use "<conn>" connection`. Consequence: with no plugin loaded the step does not exist at all.
- **A plugin must never print to stdout, and the host cannot stop it.** A file's whole output is composed by `report::render_file` and written with one `print!` (invariant 6); a plugin's line lands inside another worker's failure dump. Evidence comes back as `diagnostics` in the dispatch reply — the console shows them only on the failure path, and under `--evidence` the event stream carries them on every status.
- **Plugin libraries are deliberately leaked at exit.** `load_plugins` does `std::mem::forget(plugins.clone())` so the mapping outlives every exit path — an early `?`, `process::exit(2)`, the happy path. Running a thread-local destructor or an `atexit` handler after `dlclose` executes an unmapped page; the process is exiting anyway. That leaks the MAPPING only — instances are still dropped through FFI: a `per_worker` one when its file ends, and everything still registered by `Plugins::shutdown` after the pool drains, the call site `tests/plugin.rs::shutdown_drops_the_instance_even_after_a_failed_run` pins.
- **`<<null>>` reaches a plugin as two literal NUL bytes inside a `String`.** `serde_json` escapes them to `\u0000` on the wire, so the host's own `CString::new(request)` is fine — but after the plugin's parse the argument holds real NULs and `CString::new(arg)` returns `NulError`. The fixture's `out` helper shows the fallback. The host side is pinned by `tests/plugin.rs::a_null_sentinel_argument_crosses_the_boundary_intact`; the plugin side is still every author's own to get right.
- **A `per_worker` plugin gets one instance per FEATURE FILE, not per worker.** The manifest value states what the plugin cannot tolerate — one handle called from two workers at once — and per-file satisfies that strictly, because a file is one `run_file` task on one worker and its scenarios are sequential. It is also the grain of everything else a file owns: `World`, its `VarStack` and the per-group instance selection are all per file, so the handle lives in `World` (`PluginState::owned`), the instance is created lazily on the file's first plugin step and is dropped through FFI when the file ends. Widening it to one per worker later changes no ABI and no manifest — which is why no plugin may depend on an instance outliving the file that created it. `shared` is untouched: one lazily built instance in `Plugins::shared` for the whole run.
- **The per-scenario reset is not a broadcast, and must not become one again.** `run_file` hands `Plugins::reset_instances` exactly `world.plugins.to_reset()` — the instances its OWN file has touched — so a file with no plugin steps passes an empty list and makes no FFI call at all. The old `Plugins::reset_scenario` walked every live instance instead: one worker's scenario boundary cleared state another worker was mid-scenario in, and a failed reset was blamed on whichever file reached a boundary first, including files that had never run a plugin step. A loop over the registry «because it is simpler» reintroduces both.
- **Every handle is registered with `Plugins`, even the ones a file owns.** `Plugins::registry` is keyed by `(library index, handle)` — a handle is unique within one plugin, never across two — and every successful `init_instance` inserts there, per-file and shared alike. A panicking file loses its `World` and the handles in `owned` with it, so the registry is the only thing left for `Plugins::shutdown` to sweep after the pool drains; a per-file handle kept in `World` alone would leak a plugin's external process on exactly the path that most needs the guarantee. Know that this one path is reasoned, not pinned: no test panics a file that owns a `per_worker` instance, because the fixture's `catch_unwind` guard means a plugin cannot panic the host and there is no host-side injection point. `shutdown_sweeps_what_a_file_never_dropped` covers the sweep, not the panic that motivates it.
- **A plugin's `fields` may only describe groups its own manifest claims** (`library::check_field_groups`), for the same reason a step may not sit in an unclaimed group: the description would shadow the one belonging to whichever plugin owns that group. Reported at load, exit 2.
- **An `implicit_instance` is synthesized into `Plugins::declared` at load, and nowhere else knows it exists.** For a group the manifest lists under `implicit_instance` and the config has no `resources.<group>` section for (an empty map counts as a section), `Plugins::load` inserts an `InstanceSpec` named `default` with the manifest's body and the GLOBAL options — which is why `load` takes `&Options` — and sets it as the group default right there. `doctor`, `probe_config`, `use_instance`, `resource add` all read `declared`, so they treat it as declared for free; `PluginState::current` never learns the difference. Two consequences: `Plugins::add_defaults` EXTENDS rather than replaces, because `main::load_plugins` resolves defaults over the config's groups and never sees the implicit one; and the validation loop runs over `declared.values()`, not the config's instances, with the error labelled `plugin "<name>": implicit_instance.<group>` since there is no `resources.<group>` line to point at. Fixtures: echo declares `{"prefix": "implicit-"}`, worker declares `{}`; the rejection path is reached through `BDDKIT_WORKER_FIXTURE_REJECT_CONFIG`, set on the CHILD by the test (`Command::env`) — an env switch in a fixture, deliberate, because a manifest body is fixed and no config can make a plugin refuse it (the echo fixture has one more, `BDDKIT_ECHO_FIXTURE_BAD_SECRET_GROUP`, for the same reason: a manifest cannot be made to declare a bad `secret_groups` by config). A malformed dispatch reply that still declared `secrets` becomes a fatal result (`DispatchResult::salvage`) so they are registered; one under `privacy.min_length` is not, as everywhere.
- **A plugin field's `type` states the FORM of a value, and adds no rule about it.** `ConfigField.value_type` is `string`/`boolean`/`number`/`nonscalar`, absent meaning `string`, and `config::Scalar::from_declared` is the only place those names are mapped. It exists because a flag's value is text and the host writes the YAML: without it `--path_style false` writes `'false'`, which the plugin's own `validate_config` then refuses on every input, forever. That is why an unknown name is refused at load (`library::check_field_types`) rather than read as a string — the silent fallback IS the bug. It is not the JSON Schema #17 refused: nothing here says which values are acceptable, and `validate_config` stays the last word. Never infer the type from the value's text — a bucket may be named `true`, which is the `--set`/`--set-string` split Helm had to grow.
- **`Plugins::probe_config` returns `None` for "the plugin exports no probe", and that is never a failure.** `reset_scenario` can answer `Ok` when its symbol is absent, because "no per-scenario state to clear" genuinely is success; a reachability check that never ran has proved nothing, so `doctor --live` prints it `skipped`. Every host-side problem (unserved group, undeclared instance, malformed reply) comes back as `Some(Err(_))` — to the caller they are all "this instance could not be probed".
- **`plugin prune` is the one delete path that has no lock entry to ask `owned` about, so it has its own two guards.** A version directory is removed only when it has the shape `install` makes (a real directory holding exactly one regular file, a dynamic library — `is_install_shape`) AND no path in any live lock file of the chain, project layers included, nor in its `.before-upgrade` backup, points inside it. The backups are the load-bearing half: they are what `upgrade --rollback` restores, so a prune that ignored them would delete the versions the rollback needs. Project layers are never scanned for deletion. A directory that cannot be deleted (the shared layer, for a non-root user) is reported and the rest still go; exit 1. It is not safe against a concurrent `install`/`update`: a version is unpacked before its lock entry is written, and nothing marks that window.
- **Plugin libraries live in the layer's DATA directory, not beside its config, and are keyed by repository.** `dirs::data_dir` pairs `/etc/bddkit`→`/usr/local/lib/bddkit`, `~/.config/bddkit`→`$XDG_DATA_HOME/bddkit` (else `~/.local/share/bddkit`); project/override/Windows/macOS-shared keep libraries beside the lock. The directory is `<data>/plugins/<repo-basename>/<version>/`, not `<name>/`, because for `owner/repo` the name is only known after loading and Windows cannot rename a directory holding a mapped DLL. `remove`/`update` delete only under that directory (`manage::owned`); a hand-written entry is unregistered, never deleted. Lock writes round-trip `serde_yaml_ng::Value`: unknown keys survive, comments do not — deliberate, unlike `resource add`. The manifest-name check lives in `Plugins::load`, not `Library::load`, which `install` calls before any name is known. Before extracting into it, `fetch_into` (`manage.rs`) moves an existing `<data>/plugins/<repo>/<version>` aside to `<version>.replaced-<pid>` with no `owned()` guard — a reinstall of the same version starts clean rather than beside a stale file, and a failed one gives the old copy back: `install_into` deletes the aside copy only after the library loaded and the lock entry was written (`Fetched::commit`), and on any failure before that removes the new directory and renames the old one back (`restore`). It is aside and not a temporary extraction renamed in because Windows cannot rename a directory holding a mapped DLL; `upgrade` calls `commit` at once, since it never kept the old copy — so a same-version `upgrade` that is then refused has already lost it, a limit left because an upgrade targets a new version. A kill between the rename and a finished extraction leaves the only working copy in `<version>.replaced-<pid>`, which `prune` will list as unreferenced; installing again is the recovery. A `restore` that Windows refuses prints where the old copy is. The delete paths of `install_into` (the entry it replaced) and `remove` skip a release any lock file of the chain or a `.before-upgrade` backup still points into (`referenced_paths`, shared with `prune`), checked AFTER the entry left its own file. The aside delete is safe only because `repo` and `version` are validated single path segments before either becomes part of that path (`install::check_repo`, `install::check_segment`), from all three places a value can reach `install_into`: the CLI argument, an index entry's `repo`, and a lock entry's `source` (`update`).
