# CLAUDE.md — bddkit

Agent orientation: the fast path into this codebase for an AI agent.

`bddkit`: Gherkin-based API acceptance-testing tool in Rust. Testers write `.feature` files (readable by non-devs); the tool validates every step up front, then runs each scenario against an HTTP API and the systems behind it. `README.md` is the user-facing description of the same tool — read it for the vocabulary and config shape as a tester sees them.

## Language convention (do not get this wrong)

- **Everything in the codebase is English: code comments, runtime error messages, logs, this file, all other documentation.** No exceptions.
- **Identifiers, Gherkin step text, commit messages: English** (unchanged).
- Matcher DSL tokens (`@variableType`, `@arrayLength`, `@regExp`) are the language surface — leave as-is.
- This is about the codebase only. Conversational replies to the operator follow the operator's language (mirror Russian/Ukrainian/etc. as they write) — that is a separate axis from what goes into the repo.

## Markdown convention

**Never soft-wrap prose in `.md` files.** One paragraph — or one list item — is one physical line, however long. The renderer (browser, IDE preview, GitHub) wraps it to the reader's width; a hard line break at column 80 only fights that and makes every later edit produce a reflow diff instead of a content diff. Applies to this file, `README.md`, and anything else Markdown. Hard breaks stay meaningful where they are semantic: separate lines for list items, table rows, and code blocks.

## Architectural invariants — breaking any of these breaks the design

1. **Step matching needs no variable values.** `Registry::find` runs on RAW step text. Interpolation happens AFTER `find`, BEFORE `dispatch`, and ONLY on captured args / docstrings / table cells — never on whole step text. This is what lets `validate::check` verify every step before the first request. If you ever need a variable's value to match a step, you have broken the design — stop. A typed parameter (`{name:type}`) is the one place a value is checked against the step: the pattern accepts a literal of the type or a whole `<<…>>` slot by SHAPE, and `runner::prepare` checks the interpolated value after `find` — matching still needs no value. The step text a report, the console and the stream show is the raw feature text with ONE exception: a literal value in a `secret` parameter is written `***` (`Registry::display_text`; a value that came through a slot is left as written).
2. **State scoping is asymmetric.** Variables (`VarStack`) live per feature-FILE and persist across scenarios within it. HTTP state (`HttpState`) resets per SCENARIO (`World::reset_scenario` → `HttpState::reset`), and that reset includes the **current API resource**, which returns to `Apis::default_name()` — a scenario never inherits the API another one switched to. This mirrors Behat/Imbo — confirmed from Imbo source, not guessed. Background steps re-run before every scenario.
3. **`contains` JSON is deliberately loose; `equals` is strict.** contains = object subset + order-independent array containment + extras allowed (Imbo semantics, on purpose). equals = exact keys, element-by-element, same length. Do not "tighten" contains — that's a separate function.
4. **The dispatch match is exhaustive with NO catch-all.** `steps::dispatch` names every `StepId`. The compiler enforces completeness; a `_ =>` arm would silently defeat that when new steps are added. Never add a catch-all.
5. **Uniqueness = run_id + atomic counter.** `<<unique()>>` gives per-run prefix (time+random, sortable, greppable) + a monotonic counter → intra-run uniqueness by construction. Do not draw randomness per-value.
6. **Worker-pool runner over chains, exit codes 0/1/2/128+N.** The scheduling unit is a **chain**: files sharing a `@serial(<name>)` tag run one after another, every other file is a chain of one. `runner::build_chains` groups and sorts them by `@priority(<N>)` (higher first, default 0, a file takes the max over its tags); `runner::run_all` spawns `concurrency` tokio tasks, at least one and never more than the chain count, over one shared cursor. Each file is run by a nested `tokio::spawn` the worker awaits immediately — that bounds concurrency to the pool and isolates a panic to one file. `--fail-fast` sets an atomic flag checked at exactly two points: before a worker claims the next chain, and before it starts the next file within a chain it has already claimed. There is no checkpoint between scenarios — a file that has started always runs to completion, so a result is never partial: it stops *starting* work, it never aborts a request in flight or truncates a file mid-run. Exit: 0 all-pass, 1 any scenario failed, 2 anything that failed before the first request (validation, config, resource construction, a malformed scheduling tag) — plus ONE deliberate exception after the run: a `--junit`/`--cucumber-json` report, or the `--events` stream, that cannot be written is exit 2, because a report silently lost behind a green code is worse than a lie about when the failure happened. Failure ALWAYS dumps the HTTP exchange — masked by the privacy filter unless `--reveal`, never left out — and a file's whole output is composed by `report::render_file` and written with a single `print!` so workers cannot interleave. A fifth path is an interrupt (SIGINT/SIGTERM/SIGHUP, Ctrl-C/Ctrl-Break on Windows): `main.rs::handle_interrupt`, spawned alongside `run_all` with the `Interrupts` that `run` registered synchronously BEFORE printing `run <id>` (a signal before that is the OS default — killed, nothing cleaned, an empty event stream; one after is queued however late the task is first polled), first takes the run's ending (`RunContext::claim_end`, first caller wins — `run` takes it too once the pool drains; the winner owns the exit, the plugin shutdown and the last line of the event stream), then forces the SAME stop flag via `RunContext::force_stop` (unlike `request_stop`, not gated by `--fail-fast`), runs `Plugins::shutdown` early instead of waiting for the pool to drain, ends the event stream with the signal, and exits 128 plus the signal number (130 SIGINT, 143 SIGTERM, 129 SIGHUP; 130 for both Windows events) — a second signal skips waiting for that cleanup and exits immediately, with the FIRST signal's code. `run_file` keeps running to completion for a file already in flight; the process simply exits out from under it once cleanup (or the second signal) is done, so a file's report can be partial or missing on this one path, unlike every other exit.

## Gotchas that cost real debugging

- **A disabled step is decided by the loaded registry.** A plugin that is not loaded turns its commented steps into ordinary comments. `annotate::resolve` is the one classifier shared by `run`, `I include` and `doctor`; it matches after outline substitution and never interpolates or executes a disabled step. Background, rule Background and include annotations stay at their own execution level, and annotations after a failure still reach the stream.

- **A failure class is set where the error is born, and never parsed back out of its text.** `failure::StepError { kind, message }` is what a step returns; `FailureKind` is exhaustive in every `match`, with no catch-all. There is deliberately NO `From<String> for StepError` (nor for `AttemptError`): a `?` on a plain `String` must not compile, because a conversion that silently makes `Unclassified` is how the scheme rots. Name the class at the site: `StepError::input(…)`, `AttemptError::not_yet(…)` (an assertion that may hold later), `AttemptError::assertion(…)` (one that cannot change), `db::sql_failure` (class from the driver error), `db::db_read` (an answer that cannot be read). Helpers that only ever fail one way keep returning `String` and the step side attaches the class (`.map_err(StepError::input)`). A macro or an include re-words the message with `StepError::wrap` and keeps the inner class. A polling assertion that runs out keeps the class of its LAST attempt (`Polling::after_not_yet`), so a service that stayed down is `transport`, not `assertion`; `ReplayError::NotYet` carries that. `Unclassified` is left for the two host faults no class fits (the clock and the system entropy), built only through `StepError::host` — a new site that produces it is a bug until proven otherwise. Two known limits, deliberate: a plugin's `fatal` is always `plugin`, even from an assertion (the host cannot tell them apart without a plugin-supplied flag and an ABI bump), and `PoolTimedOut` is `db_connection` although under `concurrency` it can be the suite's own pool size. `Db::connect` is eager, so an unreachable database exits 2 before any scenario and never gets a class; `db_connection` is only what a statement or an acquisition hits mid-run (`db::sql_kind`).
- **`gen` is a reserved keyword in edition 2024.** Never name a variable/field/param `gen`; use `generator`. (`r#gen` compiles but diverges from the codebase — don't.)
- **reqwest 0.13 gates `.form()` behind the `form` feature.** Already enabled. Adding a feature to a pinned crate is allowed; bumping the version is not.
- **gherkin `Table` rows are guaranteed rectangular** ("each row is always the same length as the first row"). Table indexing after checking the header row cannot panic on parsed input.
- **Integration tests that spawn the stub AND block on `Command::output()` need a multi-thread runtime.** Use `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`. Single-threaded starves the spawned server → requests hang to timeout.
- **Two substitution syntaxes, different phases:** `<placeholder>` = Scenario Outline, substituted at parse time in `feature::substitute`. `<<variable>>` = runtime, substituted in `vars::interpolate`. `substitute` MUST leave `<<...>>` intact (a naive `replace("<key>",…)` corrupts `<<key>>` — it uses a single-pass regex `<<(\w+)>>|<(\w+)>` to protect double brackets).
- **On transport failure (`connection refused`/timeout), `HttpState::send` clears `self.last` first** so the failure dump never shows a stale prior exchange.
- **DB binds are text, the engine coerces.** Every value crosses the wire as text and the SQL carries the type: Postgres binds `$N::type` (type from schema introspection) and casts explicitly, MySQL and MariaDB bind a bare `?` and let the server coerce implicitly. The half that survives both — and the half that matters — is that **Rust never parses the value**. Consequence: a value must be a valid literal for its column type or the server rejects it.
- **The comparison operator is written on the COLUMN, never inferred from the value.** `col: v` is `=`, `col!: v` is `<>`, `col~: v` is `LIKE`, `col!~: v` is `NOT LIKE` — `split_operator` in `db/plan.rs` is the one place those suffixes are read, and an unrecognized one (`price>=`) is an error naming it rather than a lookup for a column with punctuation in its name. The direction matters more than the syntax: an earlier cut chose `LIKE` when the VALUE contained a `%`, which meant a `%` arriving through `<<...>>` from an API response could silently widen a `DELETE` — data deciding the operator is the same class of bug as inferring a config field's type from its text (see the plugin `type` gotcha). An operator anywhere a value is WRITTEN (`I have`, the SET of `I update`) is refused by `plain_column`, because reporting a missing column `slug~` sends the author to their DDL over a typo in their step. Under `~`/`!~` the value is an SQL LIKE pattern in full — `%` and `_` both match, `\%` and `\_` are the literals, backslash being the default LIKE escape on all three engines (so no `ESCAPE` clause is built; MySQL/MariaDB under `NO_BACKSLASH_ESCAPES` are the exception, where those escapes are gone). The COLUMN side goes through `cast_text` and the value binds as text (`(col)::text LIKE $1::text`, `CAST(col AS CHAR) LIKE ?`), so a non-text column matches its own text rendering rather than erroring on the operator — at the cost of the index, the right trade for a cleanup step and the wrong one for a hot path. `<<null>>` is `IS NULL` under `:` and `IS NOT NULL` under `!:`; under a LIKE it is refused, since it could only ever match nothing. What is NOT refused, and is the trap a tester meets in production: a negation carrying a VALUE never matches a NULL column — `name!: keeper` is `name <> 'keeper'`, unknown rather than true where `name` is NULL, so a cleanup written as "everything that is not X" silently leaves those rows. Ordinary three-valued logic, correctly built; documented in `README.md` because it is not what the English sentence meant. Two further ceilings ride along with `cast_text`: the comparison is against the ENGINE'S OWN text rendering, so a pattern over a timestamp is as engine-specific as `I extract` is (same gotcha, same cause), and `LIKE` folds case on MySQL/MariaDB's default `..._ci` collation where Postgres never does. And the friendly "unknown operator" error covers a trailing `!~<>=` only — `slug*:` still reports a missing column, which is the right answer for a character no operator will ever start with.
- **`<<null>>` is the only way to write a SQL NULL.** It interpolates to `vars::NULL_SENTINEL` (`\u{0}__bddkit_null__\u{0}`, NUL-bytes can't occur in `.feature` text), which the DB layer maps to SQL NULL on bind. A literal empty string `""` binds as `''`, not NULL.
- **The DB read path is blob-tolerant on purpose.** `information_schema.DATA_TYPE` arrives as a blob on MySQL 8, and an unwidened `CAST(x AS CHAR)` over a `TEXT` column does the same on MariaDB; `sqlx::Any` refuses to decode a blob into `String`. Every value therefore enters the host through `db::text_col`, which falls back to `Vec<u8>` + `from_utf8`. The obvious "fix" — a width on the cast, `CAST(x AS CHAR(255))` — decodes cleanly and trades the loud decode failure for a silent truncation. Do not add one.
- **`has_default` folds in two engine quirks, both confirmed against live servers.** MariaDB stores the literal four-character string `'NULL'` in `COLUMN_DEFAULT` for a nullable column with no default, where MySQL stores a real SQL NULL — hence the `COLUMN_DEFAULT <> 'NULL'` term. And a `STORED GENERATED` column must report a default so `build_insert` skips it, which is what Postgres's `atthasdef` already does — hence the `EXTRA LIKE '%GENERATED'` term. Neither is decoration.
- **The auto-increment id comes off the INSERT's own result packet** (`AnyQueryResult::last_insert_id()`), never a follow-up `SELECT LAST_INSERT_ID()`. That function is session state, and the pool hands the next statement whatever connection is free — at the default `concurrency` of 8 it returns another file's id, intermittently and with a plausible-looking value. The id is also filtered to `> 0`: sqlx-mysql's OK packet carries `0`, not `None`, when nothing was generated.
- **What `I extract` yields is the engine's own text rendering.** The step is portable; its value is not. `now()` reads back as `2026-08-29 15:11:50.884052+00` on Postgres and `2026-08-29 15:11:50` on MySQL/MariaDB, a boolean as `true` vs `1`, a bare `numeric` as `0` where `decimal(12,2)` is `0.00`. So `I extract` + `should be equal to` is engine-neutral over `varchar`-ish columns and nowhere else. A WHERE against the same column is unaffected — the engine coerces the bind back into its own type.
- **`wants_client_uuid` in the MySQL platform is a heuristic, and is named as one.** Postgres and MariaDB have a real `uuid` type to match on; MySQL does not, so the platform also matches `char(36)`/`varchar(36)` — on BOTH statics, MariaDB included — and a PK of that shape with no value, no default and no auto-increment is filled with a client-side UUIDv7. A `char(36)` PK holding something that is not a UUID gets one anyway. `binary(16)` is refused rather than guessed at (`check_bindable`).
- **DB tests run the compiled binary as a subprocess and need a live database.** `docker compose up -d` first, then run single-threaded (`--test-threads=1`) — the fixture schema `apibdd_it` is shared, so parallel tests race. `BDDKIT_TEST_ENGINE` picks the engine (`postgres` default, `mysql`, `mariadb`) and with it the DSN variable (`BDDKIT_TEST_DSN` / `BDDKIT_TEST_MYSQL_DSN` / `BDDKIT_TEST_MARIADB_DSN`); `tests/db_engines.rs` and `tests/db_mysql_insert.rs` read those variables directly and **skip** an engine whose variable is unset, so they pass by testing nothing unless you export them. Set `BDDKIT_TEST_TIMINGS=1` and pass `--nocapture` to print a per-test timing table. `cargo test --bin bddkit` has no DB dependency and stays fast.
- **`@serial(<name>)` orders files, it does not share their state.** `World` (and its `VarStack`) is built per file inside `run_file`, so variables do NOT flow between files of a chain. This is the natural misreading of the tag — a tester who expects `companyId` to survive into the next file gets an «undefined variable» error.
- **`I include` isolates variables via a full `VarStack` swap, not a pushed frame like macros.** The caller's globals must be invisible inside the included scenario, since file-level variables are a property of the file being run, not of every code path it can reach — a full swap (build a fresh `VarStack` at include entry, restore the original at exit) is the only way to guarantee that. The include path is a compile-time literal, resolved relative to the file the step is written in. All validation lives in the shared `validate::check` path both `run` and `doctor` call, so `doctor` needed no new stage for include-specific checks.
- **`I delete all "T"` is a full table wipe and does not know about other workers.** Under `concurrency > 1` it removes rows a parallel file is using. Same for any `I have` / `I delete … where` on fixed literals instead of `<<unique()>>`. Isolation in this tool is by data uniqueness, never by transaction rollback — parallelism does not change that rule, it just makes breaking it visible. Put such files in one `@serial(<name>)` chain, or make their data unique.
- **Debug output is not part of the atomic per-file dump.** `I am in debug mode`, `Show …`, and `Print response …` write to **stderr** as they run, so with `concurrency > 1` two workers' debug output interleaves. Deliberate — routing every debug line through a per-file buffer would delay it past the step that produced it. Set `concurrency: 1` while debugging.
- **`--fail-fast` makes a run non-reproducible.** Which files got done depends on timing. That is inherent to «stop starting new work», not a defect.
- **`init` asks nothing a flag already answered, and preselects nothing.** Every `Select`/`MultiSelect` is built WITHOUT `.default()`: dialoguer then starts with nothing highlighted and Enter does nothing until a move, which is the epic's no-preselected-answer decision (a `.default(0)` is a preselected yes). Esc on a list is `None`; Ctrl-C is different: on Unix `console` hides the cursor, then RAISES SIGINT instead of returning an error, so `command` holds it with `tokio::signal::ctrl_c` (`exit_on_ctrl_c`, installed only when prompting) — without that handler the process dies by signal with the cursor hidden — and the read comes back `Interrupted`, which `answered` maps to `None` like Esc; both end in exit 130, cursor restored, nothing written (`WRITING` only changes the message once `apply` started). dialoguer's `Input` has no Esc at all; both ways in go through `cancel()`, which prints once. Verified in a pty, not by a test. Values `init` writes go through `literal()`: the config text is `$`-expanded BEFORE it is parsed, so a typed `$` becomes `$$` and only `${NAME}` is kept as a reference. `--layer user` is passed to `install` as the explicit label, never the auto-pick (which would choose `/etc/bddkit` when only it exists), except under `--bddkit-dir`. The existing-config check runs again right before the write and also refuses the `bddkit.yaml`/`bddkit.yml` pair. The config is built as `serde_yaml_ng` values, one top-level block per key under a comment, so a DSN or URL is quoted by the serializer and never by string formatting; `resources.api` is always written, `{}` when there is no API, because `Resources::api` is required. The write is a temporary name in the same directory plus a rename (`resource::write_atomically` needs an existing file, `init` creates one). A work tree is any ancestor holding `.git` as a directory OR a file, because a linked worktree has a file. `init` writes the `telemetry` key and asks the question through `telemetry::ask_yes_no` (text: `telemetry::QUESTION_TEXT`), the same prompt `run` and `doctor` use; its payload is built in `command` after `apply`, only after a yes, and only if the layers above the key it just wrote still say on (see the telemetry gotchas). The echo fixture is `shared` and has a reset, so `doctor` refuses it under `concurrency` 8; its `init` tests pass `--parallel false`.
- **The telemetry payload is a closed struct, and a field holding suite text is a leak whatever its intent.** `telemetry/payload.rs` is numbers, booleans and enums; the only strings are the version and platform constants, the names of step groups bddkit declares, and the name and version of a plugin whose lock `source` is a repository of the `bddkit` owner (`telemetry::is_official`, read from the lock entry's `source`, which a person can edit; every other plugin is `other: true`, its name and repository never leave). Nothing the person typed is a value: a `--version` is named only after the release it names has been downloaded and has said so itself (`UpgradeInfo.to`), a plugin version typed after `@` only after the install, and a repository typed as `owner/repo` is never a name (`PluginInfo::of`). A new field is a new `SCHEMA` and a line in `docs/telemetry.md`. `failures` (schema 2) is `payload::Failures::of(&results)`: eight fixed counters, one `match` on `FailureKind` with no catch-all, and `Unclassified` counted in none — a host fault is in `failed` only, so the sum can be below `failed`. The schema number is one for every command, so a collector must accept 2 BEFORE a binary that sends it ships. Telemetry never changes an exit code and prints nothing but the question; every failure inside `telemetry::end`/`record` is silent. Debug builds never reach the real endpoint: `telemetry::endpoint` takes only `BDDKIT_TELEMETRY_URL` there. A payload is RECORDED, when the decision is on, to `telemetry-last.json` in the user layer (or the `--bddkit-dir` directory) and, if `BDDKIT_TELEMETRY_LOG` names a file, appended there as one line — the second is what the tests read — and then SENT: `telemetry::record` (async, shared by every command, so one request per command) ends in `end::send`, `POST <endpoint>/v1/run`, 500 ms connect / 1.5 s total with the same 1.5 s repeated as an outer `tokio::time::timeout` so DNS cannot outlast it (`main` leaves through `process::exit`, so a stuck resolver thread holds nothing). It is awaited at the END of the command, after the reports and the stream, not at `claim_end` as the spec's §7 has it: `exit` and `stage` are final only then. A signal during the request exits with the payload's own code instead of waiting (`send` installs its own `Interrupts`).
- **The telemetry decision is one pure function, and the question is one pure predicate.** `telemetry::decide` takes the first source with an opinion: `--telemetry`, `BDDKIT_TELEMETRY` (`true|1` on, anything else off — a typo never turns counting on), `DO_NOT_TRACK` (`1|true`, off only), the config key, then the `telemetry.yaml`/`telemetry.local.yaml` of the `.bddkit/` chain (a later layer wins; a file that does not read as `enabled: <bool>` answers no), then the default off. A config that cannot be read is `ConfigKey::Broken` and decides off unless the flag or the variable says on. `run` reads its config before anything else, so a refusal BEFORE that sends nothing (there is no `stage` for it), and a broken config exits there; the commands that need no config (`plugin`, `report`, `upgrade`, `telemetry`) never `config::load` — `Setting::discover` locates it and `config_key` reads the one key as text, because an unset `${VAR}` elsewhere in the file is not a broken config. `should_ask` is true only when nothing decided and `report::progress::can_prompt()`; `interactive()` and the payload's `ci` read the same `telemetry::ci`, which treats an empty variable as unset like the rest of the repo. The question comes LAST (after the summary, the reports and the stream flush), and only after a run that started — a refused one has an error to read first (`stage.is_none()`). `end` runs the prompt in `spawn_blocking` and races it with `Interrupts`: `console` raises SIGINT for Ctrl-C and the handlers `run` installed would otherwise swallow it, so a signal shows the cursor, stores nothing and exits with the command's own code. `ask_yes_no` is the no-`.default()` Select, and the `[y/n]` line (no default, anything else asks again) on `TERM=dumb`/unset, where dialoguer would still draw cursor movements, and on an I/O error. Verified in a pty, not by a test.
- **`run` reports through `RunProbe`, not through its exits.** `run` wraps `run_suite`, which notes on the probe the stage it is in (`Stage::Plugins` … `Resources`, cleared when the run starts) and the facts of the config; the three post-config `std::process::exit(2)` became `return Ok(2)` so the wrapper always sees the end, and the tail sets `Reports`/`Events` when a report or the stream cannot be written. Leaf steps are counted in `runner::execute_step` around `run_step` (a macro call and an `I include` are skipped, the steps they run count; `steps::group_of` for a builtin, `Plugins::usage_group` for a plugin step), into atomics fixed at startup (`telemetry::counters`), never behind a lock held across a step. A plugin failure's class (`checksum`, `network`, `no_build`, `not_found`, `refused`) is set where the error is born with `plugin::install::classed`, which wraps the error and shows exactly its text, and read back with `result_of` through any context — never parsed out of a message. Every subprocess test touching telemetry sets `BDDKIT_DIR` to a directory of its own and removes `BDDKIT_TELEMETRY`, `DO_NOT_TRACK` and the CI variables, or this machine's answer and `CI=true` change the result.
- **`I attach the file` is intercepted in `execute_step`, not routed through `dispatch`.** Like `Include`, it needs the directory of the file the step is written in (`source`, the macro file for a macro body), which `dispatch` does not carry; its `dispatch` arm is `unreachable!`. The file is READ at the step, so the recipe owns the bytes and a replayed assertion resends the same content. A literal path is checked in `validate::check`, in include bodies and in macro bodies (`Registry::validate_macros`) through the one `validate::check_attached_file`. reqwest's `.multipart()` adds its own `Content-Type` with the boundary, so every configured one is stripped first — otherwise the request carries two; the boundary header is pushed onto the recorded exchange only AFTER the real headers are applied.
- **`tokio::spawn` needs `Send + 'static`.** `execute_step` returns `Pin<Box<dyn Future + Send + 'a>>`; keep the `+ Send`. If a new step breaks it, the compiler names the value held across the `await` — scope the guard in a block. Do NOT reach for `tokio::sync::Mutex`: an async mutex held across a DB round-trip serialises the workers, which defeats the whole runner design.
- **`Config.concurrency` defaults to 8.** A suite written for a sequential runner runs 8-way parallel with no config change; set `concurrency: 1` to get the sequential behavior back until the suite is made parallel-safe.
- **SRP `hex-string` pads the client proof before hashing it into the server proof.** (`M1`/`M2` below are the SRP-6a proof messages, nothing to do with any release numbering.) The variant zero-pads the client proof `M1` to the hash's digest width before it goes into the server proof `M2`; getting that padding wrong — e.g. stripping the proof's leading zero the way some browser SRP clients do — silently produces a different `M2` about 1 login in 16, whenever the client proof's leading nibble happens to be zero.
- **Only JSON strings cross the plugin boundary — never a Rust type, never a borrowed slice.** `rustc` has no stable ABI: a `&str` or a `Vec<T>` handed to a `cdylib` built by another compiler is undefined behaviour with no diagnostic. The contract is `*mut c_char` plus the schema in `docs/plugin-authoring.md`. Adding a "just one small struct" fast path is how that becomes a heisenbug in someone else's CI.
- **The event stream has ONE writer, is opened ONCE, and nothing follows `run_finished`.** `--events <path>` (or `$BDDKIT_EVENTS`, flag wins, empty = unset, `run` only) is opened by `events::open` right after the report paths are prepared and BEFORE the config is read, and the handle is held until exit — never through `report::prepare`, which closes the file, and a FIFO's reader would see end-of-file before the first event. `events::Events` is a cloneable sender into an unbounded `std::sync::mpsc` channel (an emit never waits and never fails: after the terminator the receiver is gone and a file still in flight must not panic over it); one thread owns the file, assigns `seq`, tallies the totals from the `file_finished` lines it writes and maps the NULL sentinel, and writes a batch when the queue runs dry OR it reaches `BATCH_LIMIT` — under load the queue never runs dry, and an uncapped batch put nothing on disk until the run was over. `Events::finish` sends the terminator and JOINS the writer, from `spawn_blocking`; the writer stops after the first `run_finished`, so a second `finish` adds nothing and returns only once the first is on disk. With `RunContext::claim_end` that is what makes «nothing follows `run_finished`, and its `exit` is what the process returns» hold between the interrupt handler and `run`. The tail of `run` that waits for the writer has the handler's two-signal rule itself, because the handler is already aborted: a first signal only prints «still writing» (the run is over and its code settled, the queued lines are not thrown away), a second exits at once with the first's code — without that, a reader that stopped reading would make the process unkillable but for SIGKILL. Its `Interrupts` is registered before `claim_end`, so no signal falls between the handler and the tail. Per-file state is `events::Trace` in `World`. Every step at every depth goes through `runner::execute_step`, a thin wrapper that emits around `run_step`; the reports still see only the top-level step. A macro body step carries the DEFINITION'S line and its `index` — `ExpandedStep.line` stays the caller's, changing it would change an include-in-macro failure text. `file_finished` is emitted by the WORKER in `run_all`, not by `run_file`, so a panicked file is closed too. No subprocess test can panic a file (no host step panics on input, both fixtures `catch_unwind`), so `runner::tests::a_panicking_file_is_still_closed_in_the_stream` panics `expand_outlines` with a hand-made short `Examples` row. `--evidence` (needs `--events` or `$BDDKIT_EVENTS`, checked in `run`, not by clap's `requires`) adds `vars`, `evidence` and `attempt`: `runner::resolve` matches and interpolates a step BEFORE `step_started` so the event carries the slots from the one pass that built the `Args` (a second `<<unique()>>` pass would report values the step never sent); `HttpState` keeps each exchange only while collecting and `World::flush_evidence` emits them from `execute_step` and inside both polling loops, so the innermost step owns them and a replay's exchange precedes its `attempt`; the db emits from `ops::timed`, after the statement ran. Text over 16 KiB is filtered, written through `Artifacts::write` and referenced by a root-relative path. `Trace` evidence methods all take `&self` and are no-ops without `--evidence`.
- **`Trace` is the one gate for what evidence is written, decided per step when it starts.** `--evidence` sources (`events::Sources`, the ONE parser behind the flag, `$BDDKIT_EVIDENCE` and the config key's serde) make a step live (marked under `marked`, or `all`), deferred (`failures`) or off; `Trace::modes` runs parallel to `open`, so `evidence_on()` — and with it the plugin dispatch's `evidence` key — is the innermost step's mode. `HttpState` keeps every exchange whenever any source is active and `Trace` drops the off ones at flush. The mark (`I am collecting evidence`, the `@evidence` tag) is scenario state reset in `Trace::scenario_started`, the way `reset_scenario` clears debug; it lives in `Trace`, not `VarStack`, which is why an include's stack swap does not hide it. Deferred events are masked BEFORE they enter the `Held` buffer (they are built by the same emit code) and AGAIN at flush, with the set as it stands then — a value can become a secret after the step that sent it (`deferred_evidence_is_masked_with_the_secrets_known_when_it_is_written`). Long text is held in memory with its artifact path pre-allocated, so the event's reference is final and a passing scenario writes nothing; the per-file cap (`$BDDKIT_EVIDENCE_BUFFER`, default 64 MiB, parsed only when a source is active) bounds that long text and nothing else — held events are not counted (a `ponytail:` at `Held`). A held event's `t` is its flush time: `Tally::encode` clamps `t` to rise in `seq` order, so stamping it earlier would change nothing. `scenario_finished` flushes only for a failure AND `!RunContext::interrupted()` — not `stopped()`, which `--fail-fast` also sets: after a signal the handler's `Plugins::shutdown` can fail a plugin step still in flight, and that scenario was stopped, not failed (`a_scenario_that_fails_after_an_interrupt_drops_its_deferred_evidence`).
- **`Library`'s field order is load-bearing.** Rust drops fields in declaration order, and every function pointer in the struct points into `_library`'s mapping. `_library` is declared LAST so it is unloaded last; moving it up frees the mapping while the pointers beside it are still live. The leading underscore is the whole documentation of the field: it is never read, it exists to be dropped last.
- **A plugin instance handle is a `u64`, not a pointer.** It indexes the plugin's own table, so it is `Send + Sync` for free and can never dangle into a use-after-free on the host side — a stale or forged handle is data the plugin answers `{"status":"fatal","error":"unknown handle"}` to. The mutexes in `Plugins` protect its maps, not the handle. Do not "optimise" it back into an opaque pointer.
- **A plugin's `secret_groups` becomes synthetic `Param`s (and `ABI_VERSION` is 2: one bump for the request hint, `secrets`, `media_type` and `secret_groups` together).** `expression::plugin_params` builds one `text`/`secret` `Param` per capture group up to the last secret one (1-based in the manifest, `args[n - 1]` in the host), so `runner::prepare`, `Registry::display_text` and `step_started.vars` treat a plugin's secret group exactly as a builtin's `{name:secret}` with no second code path; nothing is type-checked. A reply's `secrets` are registered via `Redactor::secret` (so `privacy.min_length` applies) on EVERY status, before the vars or the diagnostics are read (`a_declared_media_type_replaces_the_guess_and_declared_secrets_are_masked` goes red if the loop moves later); a fatal error is masked by the run_file final pass either way. The request's `evidence` key is `Trace::evidence_on()`, sent on every polling attempt. Plugin files stay unfiltered by design (spec section 10); a plugin built for generation 1 is refused at load, and `tests/` isolates nothing from a user-layer plugin, so run them with `XDG_CONFIG_HOME`/`XDG_DATA_HOME` pointed at an empty directory on a machine that has installed plugins.
- **Plugin steps never become `StepId` variants.** They are `StepTarget::Plugin { lib, step, assertion }` — indices into `Plugins::steps()` — resolved at run time from `list_steps`, so invariant 4 (exhaustive dispatch, no catch-all) is untouched by them. The one plugin-related `StepId` is `UsePluginInstance`, the group-switch built-in.
- **`I use "<name>" <group>` is BUILT at startup from the loaded group names**, as `^I use "(?P<name>[^"]*)" (?P<group>g1|g2)$` in `Registry::add_use_group_step`. It is not a static entry in `BUILTIN_STEPS`, because `regex` has no lookahead and so cannot express "any word except api/connection" — an alternation over the real names is the only way it cannot overlap `I use "<name>" api` or `I use "<conn>" connection`. Consequence: with no plugin loaded the step does not exist at all.
- **A plugin must never print to stdout, and the host cannot stop it.** A file's whole output is composed by `report::render_file` and written with one `print!` (invariant 6); a plugin's line lands inside another worker's failure dump. Evidence comes back as `diagnostics` in the dispatch reply — the console shows them only on the failure path, and under `--evidence` the event stream carries them on every status.
- **Plugin libraries are deliberately leaked at exit.** `load_plugins` does `std::mem::forget(plugins.clone())` so the mapping outlives every exit path — an early `?`, `process::exit(2)`, the happy path. Running a thread-local destructor or an `atexit` handler after `dlclose` executes an unmapped page; the process is exiting anyway. That leaks the MAPPING only — instances are still dropped through FFI: a `per_worker` one when its file ends, and everything still registered by `Plugins::shutdown` after the pool drains, the call site `tests/plugin.rs::shutdown_drops_the_instance_even_after_a_failed_run` pins.
- **`<<null>>` reaches a plugin as two literal NUL bytes inside a `String`.** `serde_json` escapes them to `\u0000` on the wire, so the host's own `CString::new(request)` is fine — but after the plugin's parse the argument holds real NULs and `CString::new(arg)` returns `NulError`. The fixture's `out` helper shows the fallback. The host side is pinned by `tests/plugin.rs::a_null_sentinel_argument_crosses_the_boundary_intact`; the plugin side is still every author's own to get right.
- **A `per_worker` plugin gets one instance per FEATURE FILE, not per worker.** The manifest value states what the plugin cannot tolerate — one handle called from two workers at once — and per-file satisfies that strictly, because a file is one `run_file` task on one worker and its scenarios are sequential. It is also the grain of everything else a file owns: `World`, its `VarStack` and the per-group instance selection are all per file, so the handle lives in `World` (`PluginState::owned`), the instance is created lazily on the file's first plugin step and is dropped through FFI when the file ends. Widening it to one per worker later changes no ABI and no manifest — which is why no plugin may depend on an instance outliving the file that created it. `shared` is untouched: one lazily built instance in `Plugins::shared` for the whole run.
- **The per-scenario reset is not a broadcast, and must not become one again.** `run_file` hands `Plugins::reset_instances` exactly `world.plugins.to_reset()` — the instances its OWN file has touched — so a file with no plugin steps passes an empty list and makes no FFI call at all. The old `Plugins::reset_scenario` walked every live instance instead: one worker's scenario boundary cleared state another worker was mid-scenario in, and a failed reset was blamed on whichever file reached a boundary first, including files that had never run a plugin step. A loop over the registry «because it is simpler» reintroduces both.
- **Every handle is registered with `Plugins`, even the ones a file owns.** `Plugins::registry` is keyed by `(library index, handle)` — a handle is unique within one plugin, never across two — and every successful `init_instance` inserts there, per-file and shared alike. A panicking file loses its `World` and the handles in `owned` with it, so the registry is the only thing left for `Plugins::shutdown` to sweep after the pool drains; a per-file handle kept in `World` alone would leak a plugin's external process on exactly the path that most needs the guarantee. Know that this one path is reasoned, not pinned: no test panics a file that owns a `per_worker` instance, because the fixture's `catch_unwind` guard means a plugin cannot panic the host and there is no host-side injection point. `shutdown_sweeps_what_a_file_never_dropped` covers the sweep, not the panic that motivates it.
- **Step declarations are Cucumber Expressions with a bddkit extension, and `steps/expression.rs` is the ONLY parser of them.** Builtins and macro templates alike: optional `(text)`, alternation `a/b`, escapes `\(` `\{` `\/` `\\`, per cucumber.io. Cucumber parameters have a type and no name; bddkit writes `{name}` / `{name:type}` into the type slot and splits it off — legal by the grammar (a type name may hold any character but `{ } ( / \`), but OUR convention, and documented as such. One `expression::compile` yields the regex, the conflict tokens and the `steps list` template from a single AST; a second reader of the same text is exactly the drift #66 removed (`builtin_patterns` re-read the regex by hand and went blind when #50 added a construct it did not know). Cucumber's own `{string}`/`{int}` are never used: `{string}` accepts single quotes and `\"` escapes, which would widen the `.feature` language. An alternation spans the whole whitespace-delimited word, optional parts included — `(the )post/article` is `(the )post` | `article` — so tests and examples keep an optional and an alternation in separate words.
- **An optional may not hold a parameter** (a Cucumber rule the crate enforces). That is why `Include`/`IncludeScenario` are each declared twice, without and with `with prefix "{prefix}"`, and why `run_include` reads the prefix with `caps.get(…)` rather than by index.
- **Whether a BARE parameter takes quotes is its type's `Quoting` (`expression.rs`), and quotes the template writes are always literal.** `text`/`secret` are `Required` (the host adds the quotes), `uint`/`int`/`float`/`word`/`method` are `Optional` (`"(R)"|(R)`, two capture groups: `Param::groups` says which, `expression::arguments` and `Param::span` read them — never index captures by parameter position), `any` is as written. A parameter is bare unless an odd number of `"` precede it in the template. An `Optional` type may never match whitespace or `"` (`an_optional_type_cannot_hold_whitespace_or_a_quote`). A macro with an untyped quoted `"{x}"` before a bare typed parameter can overlap a builtin ending in a quoted `any` and is refused at startup; type it `{x:text}`.
- **`secret` is `text` with a flag.** Same regex, same conflict shape (`secret_matches_exactly_what_text_matches` pins it); `ParamType::secret` is what `runner::prepare` registers into the file's set and `Registry::display_text` hides from step text. A new builtin that takes a credential declares it `{name:secret}`, and a step that DERIVES a secret from its inputs (SRP's `_a` and `_sessionKey`) registers it itself with `w.redactor.secret`.
- **A type constrains literal text; a `<<var>>` in a typed position is checked after interpolation.** `uint` compiles to `[0-9]+|<<…>>` where the slot is the cheap `expression::SLOT_SHAPE` (the exact grammar `vars::PLACEHOLDER` costs ~0.5 s per use in a debug build once the cucumber-expressions crate expands its `\w`), and `Registry::find_with_params` drops a hit whose typed argument starts with `<<` but is not `vars::is_whole_slot`, so a malformed slot is still refused before the first request. `Param::check` fails the step (exit 1) when the interpolated value is not a `uint`. A conflict class may be WIDER than its type's regex, never narrower — which is why a typed parameter also contributes the placeholder shape to the conflict variants.
- **Report paths are truncated before the config is read, in `run` and `doctor` alike.** `report::prepare` is the first thing `run` does — before `config::load` — so a run that dies on its config leaves an EMPTY `--junit`/`--cucumber-json` file a CI parser rejects loudly, never yesterday's green one; `tests/acceptance.rs::a_report_path_is_truncated_before_the_config_is_read` pins the order. `doctor` calls the same function for its `reports` stage, also first, so it truncates too — that is the promise "the same check", not a side effect to remove. The result model carries per-step status and timing (`report::StepResult`, `passed`/`failed`/`skipped` only) because both formats need them; the console never prints them. The XML writer is hand-rolled: `report::xml` escapes the five characters and replaces what XML 1.0 cannot carry at all (NUL — the `<<null>>` sentinel — and other control characters) with U+FFFD, since a `&#0;` reference is just as invalid as the byte.
- **`doctor` is not a second validator, and its exit codes are not `run`'s.** Every static stage is a function `run` itself calls, in `run`'s own order; a check `doctor` performs and `run` does not is a bug in `doctor`, so a new rule goes in the **shared** path — the zero `timeout_secs` refusal lives in `http::ApiResource::new`, and every declared SRP resource (not only the default) is validated in `run` itself, both so `doctor` cannot be the stricter of the two. The pair `tests/acceptance.rs::run_refuses_a_malformed_srp_resource_that_is_not_the_default` and `http::tests::a_zero_timeout_is_refused_when_the_resource_is_built` is what keeps that honest. The ONE deliberate exception is `validate::unserved_resources` — a step of a group with nothing declared (`resources.api: {}` under an HTTP step, a plugin group emptied to switch its `implicit_instance` off): `run` cannot refuse it, since a `--tag` may keep the scenario out and the selection is unknown until it runs, so the check lives beside `validate::check` rather than in it and only `doctor`, which checks every scenario whatever the config's `tags` select (they only decide whether there is anything to run), calls it. A `Failed` row in the `steps` stage, once per file and group; not a new `Status`. And `doctor` exits **0 or 1 only** — never 2. An unparseable config is the most ordinary thing it has to report, not a reason to answer in a different currency; a script's rule stays "0 = clean, 1 = something to fix".
- **The include hints live in `doctor.rs`, not in `validate::check`, on purpose.** An `extract` right after `I include` that the helper does not export, and an `@exports` name no step of the helper writes, are guesses (a plugin step can set a variable the host cannot see), so they ride in the `steps` row's detail like the unmatched-comment lines and never fail it; the "a check `doctor` makes and `run` does not is a bug" rule is for refusals, not hints. The writer list (`written_names`) gives up (no hint) on SRP/AES, a plugin step, a step that matches nothing, a glob export and a `<<slot>>` or Outline `<column>` name, and the DB result names (`last_insert_*`, `updated_*`, `deleted_*`) are never reported. Only loaded feature files are scanned as callers.
- **`doctor`'s stage list is not `validate::check` plus resources — it must reach every pre-run check `run` makes.** Three were missed on the first pass and each was a green `doctor` in front of a `run` that exits 2: `runner::build_chains` (a malformed `@priority`/`@serial`), the empty selection, and — subtlest — a DSN whose *scheme* is fine but whose URL the driver cannot parse, since `AnyPoolOptions::connect` parses the whole thing before opening anything (hence the `AnyConnectOptions::from_str` in `db::check_dsn`). When a new pre-first-request check is added to `run`, walk `run()` end to end and add it here too. `doctor::check_features` loads the feature files once and reports two stages from them; scheduling and the parse errors are reported even when the step vocabulary is skipped, because neither depends on it.
- **A bare `doctor` opens no socket of its own, and that is the promise the command is sold on.** `--live` is the only thing the host probes with, `tests/acceptance.rs::doctor_without_live_leaves_an_unreachable_base_url_alone` pins it, and every static stage must stay callable on a train. The one caveat is not the host's: the plugin stage runs `lib.validate_config` through FFI per declared instance (`plugin/mod.rs`), and what third-party code does there is its own business. The live DB probe calls `db::Db::connect` with a ONE-ENTRY map per connection — not to name the dead DSN, which `Db::connect` already does, but because the whole-map call returns at the FIRST failure and a second dead connection would never be probed; `#[derive(Clone)]` on `config::Connection` exists for that. Under `--live` an API answering 404 or 500 is `ok`: reachability is the question, the application's own routing is not.
- **The host's resource field tables are hand-written, and one drift direction is deliberately uncovered.** `API_FIELDS` / `DB_FIELDS` / `SRP_FIELDS` in `config.rs` describe `ApiConfig` / `Connection` / `SrpConfig` for `bddkit resource fields`; Rust has no reflection to derive them. `config::tests::check_table` catches a renamed field and a flipped `required` (for every field the table calls required, a document omitting it must fail to deserialize; the whole document must succeed), and does NOT catch a field added to the struct and forgotten in the table — the benign direction, where the key still works and is only undocumented. Add the entry when you add the field.
- **A plugin's `fields` may only describe groups its own manifest claims** (`library::check_field_groups`), for the same reason a step may not sit in an unclaimed group: the description would shadow the one belonging to whichever plugin owns that group. Reported at load, exit 2.
- **An `implicit_instance` is synthesized into `Plugins::declared` at load, and nowhere else knows it exists.** For a group the manifest lists under `implicit_instance` and the config has no `resources.<group>` section for (an empty map counts as a section), `Plugins::load` inserts an `InstanceSpec` named `default` with the manifest's body and the GLOBAL options — which is why `load` takes `&Options` — and sets it as the group default right there. `doctor`, `probe_config`, `use_instance`, `resource add` all read `declared`, so they treat it as declared for free; `PluginState::current` never learns the difference. Two consequences: `Plugins::add_defaults` EXTENDS rather than replaces, because `main::load_plugins` resolves defaults over the config's groups and never sees the implicit one; and the validation loop runs over `declared.values()`, not the config's instances, with the error labelled `plugin "<name>": implicit_instance.<group>` since there is no `resources.<group>` line to point at. Fixtures: echo declares `{"prefix": "implicit-"}`, worker declares `{}`; the rejection path is reached through `BDDKIT_WORKER_FIXTURE_REJECT_CONFIG`, set on the CHILD by the test (`Command::env`) — an env switch in a fixture, deliberate, because a manifest body is fixed and no config can make a plugin refuse it (the echo fixture has one more, `BDDKIT_ECHO_FIXTURE_BAD_SECRET_GROUP`, for the same reason: a manifest cannot be made to declare a bad `secret_groups` by config). A malformed dispatch reply that still declared `secrets` becomes a fatal result (`DispatchResult::salvage`) so they are registered; one under `privacy.min_length` is not, as everywhere.
- **A plugin field's `type` states the FORM of a value, and adds no rule about it.** `ConfigField.value_type` is `string`/`boolean`/`number`/`nonscalar`, absent meaning `string`, and `config::Scalar::from_declared` is the only place those names are mapped. It exists because a flag's value is text and the host writes the YAML: without it `--path_style false` writes `'false'`, which the plugin's own `validate_config` then refuses on every input, forever. That is why an unknown name is refused at load (`library::check_field_types`) rather than read as a string — the silent fallback IS the bug. It is not the JSON Schema #17 refused: nothing here says which values are acceptable, and `validate_config` stays the last word. Never infer the type from the value's text — a bucket may be named `true`, which is the `--set`/`--set-string` split Helm had to grow.
- **`Plugins::probe_config` returns `None` for "the plugin exports no probe", and that is never a failure.** `reset_scenario` can answer `Ok` when its symbol is absent, because "no per-scenario state to clear" genuinely is success; a reachability check that never ran has proved nothing, so `doctor --live` prints it `skipped`. Every host-side problem (unserved group, undeclared instance, malformed reply) comes back as `Some(Err(_))` — to the caller they are all "this instance could not be probed".
- **`resource add` never rewrites a line, and that is the whole reason comments survive.** The block is spliced in after an anchor line — the `<group>:` line, or `resources:` when the group is new — and the spliced text is then re-parsed and compared as a `Value` against the original plus the new resource; anything but equality writes nothing and exits 1. So an existing resource is refused rather than replaced, and the splice works on byte offsets rather than `str::lines`, which drops a trailing newline and hides `\r\n`. The temptation to "just rewrite the block" is how a suite loses the comments inside it.
- **`resources.<group>` bodies cannot contain a YAML tag.** The groups map is `#[serde(flatten)]`, and serde's buffering for flattened fields cannot represent `key: !Foo bar` — it fails with "untagged and internally tagged enums do not support enum input", which does not obviously mean "you used a tag". Anchors and aliases are fine. `api`, `db`, `srp` and `connection` are refused as group names outright (`HOST_GROUPS`).
- **`--config` is optional and resolved the same way everywhere.** `config::resolve_config_path` tries the flag, then `$BDDKIT_CONFIG`, then `./bddkit.yaml`/`./bddkit.yml` in the working directory (both present is refused, naming both) — no walk-up into parent directories, because `paths`/`macro_paths` resolve against the working directory, not the config file's, and a config found in a parent would then select the wrong feature files. An explicit `--config` or `BDDKIT_CONFIG` pointing at a missing file is never a silent fallback to the default — `resolve_config_path` does not check existence for those two, so the ordinary "failed to read config" error from `load` fires instead. `run` and `resource add` treat "nothing found" as their normal "run not started" / "nothing written" failure (exit 2 / 1); `doctor` reports it as an ordinary failed `config` row (exit 1, never 2, same as every other doctor finding) and states which source won next to the path for a human (`(--config)` / `(BDDKIT_CONFIG)` / `(found in working directory)`) and as its own `config_source` field for `--json` (`"flag"`/`"env"`/`"discovered"`, absent when nothing was found) — a consumer should never have to parse that suffix back out of `config`. `steps list` and `resource fields` pick up the default too so a bare invocation inside a suite directory shows that suite's plugin vocabulary — `--no-config`, conflicting with `--config`, is the escape back to builtins-only, and it must skip resolution entirely rather than merely ignoring a discovered file, so a broken `bddkit.yaml` cannot block the lookup either.
- **`--config cfg.yaml` has an empty parent, and `std::path::absolute` rejects an empty path.** `dirs::project` (the project-layer walk-up) needs an absolute starting point, so `main.rs::config_dir` (`pub(crate)`, shared by `load_plugins` and `doctor::check`) maps a `parent()` of `""` to `.` before handing it to `dirs::layers` — a bare `.parent()` alone does not protect this, the empty-string case has to be caught explicitly. `dirs::tests::a_relative_config_dir_walks_real_parents` pins the fix, not just the symptom.
- **`upgrade` trusts only its receipt, and the staged binary is the only judge of the new plugins.** `install.sh`/`install.ps1` write `install.json` (`path`, `version`, `target`) into `dirs::user_data` — computed from the environment alone, so `--bddkit-dir` cannot hide it — and `upgrade` proceeds only when the canonicalised `current_exe()` equals the receipt's path (the one exception: `--rollback` may run as `<data>/previous/bddkit`, which is how a new binary that will not start is undone). The running process speaks the OLD plugin ABI, so a new-ABI plugin is fetched with `Context::fetch_into` (no `Library::load`, no lock write, no deleting the previous version) and vouched for by `<staged> plugin check <path>`, a hidden command; `install_into` is the load-and-register half only `plugin install`/`update` use. `install::host_release` takes the ABI as a parameter for the same reason. The staging directory sits beside the binary, not in the temp directory: a rename cannot cross filesystems, and a directory that cannot be created there is the «not writable» refusal before a byte is downloaded. Nothing is deleted before the switch, and `Cleanup` removes only the plugin directories THIS run created. `<data>/previous/pending.json` names exactly the lock files this upgrade backed up as `<file>.before-upgrade`, so a rollback after a same-ABI upgrade does not restore backups an older one left; the next switch drops the old ones. Tests never replace `CARGO_BIN_EXE_bddkit`: they copy it into a sandbox and serve a `#!/bin/sh` script as the «new release» (`Stub::publish_bddkit`), which is also why the hooks live in the script and not in the host. Windows (`self-replace`) is not exercised by any test.
- **`plugin prune` is the one delete path that has no lock entry to ask `owned` about, so it has its own two guards.** A version directory is removed only when it has the shape `install` makes (a real directory holding exactly one regular file, a dynamic library — `is_install_shape`) AND no path in any live lock file of the chain, project layers included, nor in its `.before-upgrade` backup, points inside it. The backups are the load-bearing half: they are what `upgrade --rollback` restores, so a prune that ignored them would delete the versions the rollback needs. Project layers are never scanned for deletion. A directory that cannot be deleted (the shared layer, for a non-root user) is reported and the rest still go; exit 1. It is not safe against a concurrent `install`/`update`: a version is unpacked before its lock entry is written, and nothing marks that window.
- **Plugin libraries live in the layer's DATA directory, not beside its config, and are keyed by repository.** `dirs::data_dir` pairs `/etc/bddkit`→`/usr/local/lib/bddkit`, `~/.config/bddkit`→`$XDG_DATA_HOME/bddkit` (else `~/.local/share/bddkit`); project/override/Windows/macOS-shared keep libraries beside the lock. The directory is `<data>/plugins/<repo-basename>/<version>/`, not `<name>/`, because for `owner/repo` the name is only known after loading and Windows cannot rename a directory holding a mapped DLL. `remove`/`update` delete only under that directory (`manage::owned`); a hand-written entry is unregistered, never deleted. Lock writes round-trip `serde_yaml_ng::Value`: unknown keys survive, comments do not — deliberate, unlike `resource add`. The manifest-name check lives in `Plugins::load`, not `Library::load`, which `install` calls before any name is known. Before extracting into it, `fetch_into` (`manage.rs`) moves an existing `<data>/plugins/<repo>/<version>` aside to `<version>.replaced-<pid>` with no `owned()` guard — a reinstall of the same version starts clean rather than beside a stale file, and a failed one gives the old copy back: `install_into` deletes the aside copy only after the library loaded and the lock entry was written (`Fetched::commit`), and on any failure before that removes the new directory and renames the old one back (`restore`). It is aside and not a temporary extraction renamed in because Windows cannot rename a directory holding a mapped DLL; `upgrade` calls `commit` at once, since it never kept the old copy — so a same-version `upgrade` that is then refused has already lost it, a limit left because an upgrade targets a new version. A kill between the rename and a finished extraction leaves the only working copy in `<version>.replaced-<pid>`, which `prune` will list as unreferenced; installing again is the recovery. A `restore` that Windows refuses prints where the old copy is. The delete paths of `install_into` (the entry it replaced) and `remove` skip a release any lock file of the chain or a `.before-upgrade` backup still points into (`referenced_paths`, shared with `prune`), checked AFTER the entry left its own file. The aside delete is safe only because `repo` and `version` are validated single path segments before either becomes part of that path (`install::check_repo`, `install::check_segment`), from all three places a value can reach `install_into`: the CLI argument, an index entry's `repo`, and a lock entry's `source` (`update`).

## Privacy (secrets are masked, never rewritten)

The spec is `docs/events-design.md` section 7; the tester's view is the README's Privacy section. The mechanism is one set of secret values and one filter; the rules that keep it correct:

- **Masking is render-only.** `Exchange`, `RequestRecipe`, `VarStack` values and plugin arguments keep their real values — assertions, polling replays and plugins depend on them. Text is masked where it is PRODUCED for a human or a file, never in the state it came from.
- **One handle per file, shared on purpose.** `World::redactor` is a `Redactor` forked from `RunContext::redactor` at the start of `run_file`, and `VarStack`, `HttpState` and `Trace` hold clones of it. `I include` swaps the whole `VarStack` for a fresh one, so `run_include` hands the fresh stack the same handle — drop that line and a secret saved inside an include is not masked in the caller's failure (`a_secret_saved_inside_an_include_is_masked_in_the_callers_failure`). The mutex inside is a `std::sync::Mutex` and is never held across an await.
- **Order is position, then value, then the cut.** Values under sensitive names are hidden by position (`Exchange::spans`, `json_hits`), then the set is applied, THEN a body is cut to 600 characters, so a secret straddling the cut cannot show its first characters. Mask before escaping too: strings are masked before they become JSON (`Trace`, `doctor::Report::row`); reports are XML-escaped only after `run_file`'s final masking pass.
- **Register before the request leaves.** `HttpState` registers a header, query value, form value or JSON body when the STEP sets it (a scenario that fails before sending still prints that step's text in its report), and `execute` again before `client.execute` (a literal `?token=` in the path, a default header, a signed header), because a refused connection's error quotes the URL; the response half is registered after. Dropping either half breaks a test in `tests/acceptance.rs` (`a_json_value_sent_under_a_sensitive_name_is_secret_everywhere_afterwards`, `a_token_only_the_response_carries_is_masked_by_the_response_scan`).
- **Reports get a final pass.** A value can join the set after the step that mentions it was recorded, so `run_file` masks every scenario name, failure, step text and warning once more at the end. The event stream is masked as it is emitted and never rewritten (spec 7.8).
- **The process sink is append-only.** `privacy::record` is called by `main::run`/`doctor_command` (via `set_flags`) and by `config::load_str` BEFORE the typed parse, because a serde type error quotes the offending value; `mask_text` masks the `error:` lines, `doctor` rows and the `resource add` block from it. Tests share the process, so a unit test that loads a config must never set `reveal` or a large `min_length`.
- **`display_text` is for every output that names a step** — console, both reports, the stream, polling messages, the debug `macro` line, nested macro and include errors. A new place that prints `step.text` raw leaks a short literal secret (shorter than `min_length` never joins the set; only position can hide it).
- **Error text that quotes input is a leak.** `dotenvy`'s own message quotes the whole `NAME=secret` line, so `load_env_file` reports a file and a position only. A new parser error on a config path gets the same scrutiny.
- **Every configuration option has three forms: a config key, a flag and an environment variable, and the highest wins — flag, then environment, then config, then the default.** The names are mechanical (`privacy.min_length` → `--privacy-min-length` → `BDDKIT_PRIVACY_MIN_LENGTH`), an empty variable is unset, a boolean is `true|false|1|0`, and a list option comes as `x` (adds) and `x_only` (replaces). The privacy options (`privacy.rs`) and the run's own options (`settings.rs`: one `SettingsArgs` flattened into `run` and `doctor`, one `settings::resolve` with the environment injected, `Config::apply` laying it over the loaded file and resolving again) follow it; the run's lists (`tags`, `paths`, `macro_paths`) are the one deviation, replacing the config's list with no `_only` twin; the exceptions are what cannot have all three: the config's own location, the report and events paths (opened before the config is read), per-resource keys, the `default_<group>` of a plugin group and debug mode (a per-scenario step).

## Resources and selection

APIs, databases and SRP configurations are global named resources (`resources.api` / `resources.db` / `resources.srp`, plus optional `default_api` / `default_db` / `default_srp`, inferred when a kind has exactly one resource). Any scenario reaches any of them by name — `I use "<name>" api`, `I use "<conn>" connection`. One `reqwest::Client` per API resource, built once into an `Arc<Apis>`; one `sqlx::Any` pool per DB connection for the whole run (`Db::connect`), each carrying the `&'static dyn Platform` its DSN scheme selects — plus, for the `mysql://` family, one `SELECT VERSION()` per connection to tell MySQL from MariaDB.

Any other `resources.<group>` key is a **plugin group**: the host keeps the body verbatim (minus the reserved `options` key), a loaded `cdylib` validates and serves it, and `default_<group>` follows the same inference rule. Selection is `I use "<name>" <group>` and resets per scenario like the API does. Plugins come from a layered `.bddkit/` chain — shared, user, project directories, each read as `plugins.yaml` then `plugins.local.yaml`, a later entry overriding an earlier one of the same plugin `name` (`dirs.rs`, `plugin/lock.rs`) — or from a single `--bddkit-dir`/`BDDKIT_DIR` directory that replaces the whole chain; by default this is machine state, never committed with the suite (`plugins.local.yaml` is meant to be gitignored), except a deliberate `bddkit plugin install --layer project` (or `project.local`), which vendors `.bddkit/plugins/` into the repository on purpose. The whole authoring contract is `docs/plugin-authoring.md` and the worked example is `tests/fixtures/echo-plugin`.

Test selection lives on the CLI: a positional path argument overrides `cfg.paths`, and a repeatable `--tag` filters scenarios (feature-level tags are merged onto every scenario at load; an empty selection exits 2).

**Known gap, deliberate:** `resources.srp` accepts multiple named SRP resources, but only the default one is reachable — no step exists yet to select a non-default one by name.

## Macros (declarative domain steps)

YAML files listed under `macro_paths` declare domain steps (`I login as user "..."`) without a rebuild. Matching is transparent — a step is a built-in or a macro, the caller can't tell. Macros take scalar parameters, run in isolated frames that publish results through named/glob `exports`, and may nest up to depth 16. Conflicts and cycles are caught at startup validation (exit 2). Macro call tables/docstrings and loops are intentionally out of scope. Templates are Cucumber Expressions with typed parameters — see the step-declarations gotcha.

## Eventual assertions

`I expect the next assertion to pass ...` arms exactly one future assertion: inputs are interpolated once, a later modifier silently replaces an earlier one, and an unconsumed modifier is discarded at scenario end or reset. DB attempts query the current connection anew; an HTTP response assertion first checks the saved exchange, then replays its immutable original request at its original API after each mismatch, freshly signing Hawk on every replay. Polling options are inherited global → resource (`options.rs`). A `vars`-group assertion (`variable "x" should …`) answers `Fatal`, never `NotYet`, on a mismatch — nothing runs between attempts, so its subject cannot change (`vars::settled`); a runner test that needs a pollable assertion without network uses the echo plugin's `the echo counter should reach N`, not a variable.

## Adding a built-in step

1. Add a `StepId` variant + its entry to `BUILTIN_STEPS` in `steps/mod.rs`: group, Cucumber Expression, one-line English description. A parameter is `"{name}"` (quoted text) or `{name:type}` with a type from `expression::TYPES` — the name is what `bddkit steps list` prints as `<name>`. An optional part cannot hold a parameter: declare two entries with the same `StepId` instead. Keep the ambiguity test green — if two expressions overlap, fix the EXPRESSION, not the table order.
2. Write the step fn in `steps/{api,assert,vars,db,debug,srp}.rs`.
3. Add a dispatch arm (compiler forces this — no catch-all).
4. Optionally translate the description in `locales/steps.{ru,lv}.yaml`, keyed by the `StepId` variant name. Skipping this is fine — an untranslated step falls back to English per step.

Verb convention: `I <action>` mutates, `should` asserts, `the … is` sets a request param. No verb does both directions.

## Database layer

DB steps live in `steps/db.rs`; SQL is built in `db/plan.rs`, dialected in `db/platform/` and run in `db/ops.rs`. The connection a scenario starts on comes from `default_db` (or is the single declared connection). Table refs are `[connection:][schema.]table` — on Postgres an unqualified name resolves through `search_path`, on MySQL/MariaDB through the DSN's own database, and there the qualifier is a *database* name. Full Gherkin vocabulary (all in `BUILTIN_STEPS`):

- **Insert** — `I have "<table>" with "<pairs>"` (one-liner) · `I have "<table>" where:` (data table, columns as header) · `I have:` (multi-table wide form, first column = table). Schema introspection drives PK/NOT-NULL fill: value given → use it; identity/serial/`AUTO_INCREMENT` or column with a default → omit from INSERT, let the engine generate; no-default `uuid` PK (or `char(36)` on MySQL) → UUIDv7 client-side; NOT-NULL timestamp with no value → `now()`; otherwise fail naming the column.
- **Update** — `I update "<table>" with "<pairs>" where "<cond>"`.
- **Delete** — `I delete "<table>" where "<cond>"` · `I delete all "<table>"` (no WHERE, full wipe).
- **Read into a var** — `I extract "<column>" from "<table>" with "<where>" as "<var>"`.
- **Assert row presence** — `I should have "<table>" with "<pairs>"` / `with:` · `I should not have "<table>" with "<pairs>"` / `with:`.
- **Routines / sequences** — `I call procedure "<name>" with "<args>"` · `I call function "<name>" with "<args>" as "<var>"` · `I get next value of sequence "<name>" as "<var>"`.
- **Connection / debug** — `I use "<conn>" connection` (its API counterpart is `I use "<name>" api`, a `steps/api.rs` step: it switches the target API resource, replaces the headers with that resource's `default_headers`, clears the pending query/body/form/attachments, and deliberately KEEPS `last`) · `I am in debug mode` / `I am not in debug mode` (debug prints the generated SQL + binds).

`<pairs>`/`<cond>`/`<where>` are one-liners: comma-separated `col: value`; a literal comma inside a value is escaped `\,`. In a CONDITION the column may carry an operator suffix — `col!:` (`<>`), `col~:` (`LIKE`), `col!~:` (`NOT LIKE`), plain `col:` being `=`; the same column may appear twice, so a range is `amount>=: …` shaped as two pairs once ordering operators exist. Where a value is WRITTEN — `I have`, the SET of `I update` — a suffix is an error, not a column name. `<<...>>` is runtime variable interpolation (`vars::interpolate`), and `<<null>>` yields a SQL NULL (see Gotchas). In a WHERE, a NULL value compiles to `col IS NULL` (`col!:` → `IS NOT NULL`, no bind either way).

**Result variables** written back after a step (readable as `<<...>>`):
- `last_insert_*` — PK values from the last insert: `last_insert_id_<table>` for a single-column `id` PK, `last_insert_<table>_<col>` per column for other/composite PKs, plus a `_<index>` suffix in multi-row/`I have:` inserts.
- `updated_<table>` — rows affected by the last update on that table.
- `deleted_<table>` — rows affected by the last delete on that table.

**Known ceilings / limitations (intentional, not bugs — do NOT "fix" without a spec change):**
- **`I extract` cannot distinguish SQL NULL from empty string.** It runs `SELECT <cast_text(col)> … LIMIT 1` — `(col)::text` on Postgres, `CAST(col AS CHAR)` on MySQL/MariaDB — and coerces a NULL result to `""` (`unwrap_or_default`). A row that is NULL and a row that is `''` both yield `""` in the variable. The text it does yield is the engine's own (see Gotchas).
- **`I extract` reads only the first matching row** (`LIMIT 1`); the WHERE is not required to be unique and no ordering is imposed.
- **Isolation is by data uniqueness, not transaction rollback.** The service-under-test reads through its own connection and won't see uncommitted rows, so tests can't wrap work in a rollback — they rely on `<<unique()>>`-scoped data instead.
- **A connection is bound to what its DSN names.** On Postgres that is one database and many schemas can share the connection (`schema.table`); a second database needs a second entry in `resources.db`. On MySQL/MariaDB a schema IS a database, so `other_db.table` reaches a second one over the same connection where privileges allow — and `search_path` is refused at startup rather than ignored, because there is no session-level equivalent to ignore it into.
- **Not every step reaches every engine.** MySQL has no sequences (`I get next value of sequence` fails naming the platform) and no `RETURNING`, so a PK filled by a server-side `DEFAULT` that is not `AUTO_INCREMENT` is refused *before* the INSERT runs rather than after it commits; MariaDB has both, from 10.5 — older is refused by nothing and fails on a syntax error from the server. `binary`/`varbinary` columns are refused at any width. `README.md` states the support level and `examples/README.md` carries the per-engine table; keep all three in step.

## Dev workflow

- do not use `superpowers` for simple tasks and non-code changes.
- when changing Rust code, use `rust-best-practices` skill.
- TDD per task: failing test → RED → implement → GREEN → commit. Tests assert real behavior, never mock theater.
- Dependency VERSIONS are frozen (features may be added). Edition 2024, toolchain 1.97 — CI pins the exact version in the workflows (`toolchain: "1.97.1"`), so a new clippy lint in a fresh stable can never redden an unrelated PR. Do NOT pin it with a `rust-toolchain.toml`: on a machine whose `stable` already is that version rustup installs a second copy of the same toolchain and can leave it half-installed.
- `cargo test` (unit + `tests/acceptance.rs` e2e against the axum stub). `cargo clippy --all-targets` must be clean — no warnings. `cargo fmt --check` must be clean too, at the root and in both fixture crates (`tests/fixtures/echo-plugin`, `tests/fixtures/worker-plugin`) — run `cargo fmt` (and the fixture equivalents) before committing rather than letting CI catch it. `HttpState::current` carries an `#[allow(dead_code)]` because only tests read it; that is correct, don't delete the method.
- `selftest/` runs the binary on a fixture that fails on purpose, through the published `exec` plugin, and asserts on the console, the JUnit report and the stream (`./target/debug/bddkit run --config selftest/bddkit.yaml`, after `bddkit plugin install exec`; CI's "Self-test" step does the same). It is not `examples/`: that must stay green. A new cross-cutting behaviour that only shows in bddkit's own output (masking, reports, exit codes) gets a scenario there as well as a Rust test.
- Acceptance gate: never weaken a `.feature` or an assertion to force green. A red feature file means a real bug — fix the code or report it, don't patch the test.
- Load-bearing acceptance tests, each pinning an invariant that is easy to break silently: `one_scenario_can_call_two_different_apis` (resources), `two_feature_files_run_at_the_same_time` + `a_single_worker_cannot_release_the_barrier` + `two_files_in_one_serial_chain_never_run_together` (parallelism and per-file variable isolation, proven by a barrier stub rather than timing), `tests/features/srp_login.feature` (registration + authenticated login end to end).
- Subagent reports have miscounted tests and quoted non-existent text — verify claims against files, don't trust report prose.
