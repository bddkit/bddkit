# CLAUDE.md — bddkit

Agent orientation: the fast path into this codebase for an AI agent.

`bddkit`: Gherkin-based API acceptance-testing tool in Rust. Testers write `.feature` files (readable by non-devs); the tool validates every step up front, then runs each scenario against an HTTP API and the systems behind it. `README.md` is the user-facing description of the same tool — read it for the vocabulary and config shape as a tester sees them.

## Language convention (do not get this wrong)

- **Everything in the codebase is English: code comments, runtime error messages, logs, this file, all other documentation.** No exceptions.
- **Identifiers, Gherkin step text, commit messages: English** (unchanged).
- Matcher DSL tokens (`@variableType`, `@arrayLength`, `@regExp`) are the language surface — leave as-is.
- This is about the codebase only. Conversational replies to the operator follow the operator's language (mirror Russian/Ukrainian/etc. as they write) — that is a separate axis from what goes into the repo.

## Markdown convention

**Never soft-wrap prose in `.md` files.** One paragraph — or one list item — is one physical line, however long. The renderer (browser, IDE preview, GitHub) wraps it to the reader's width; a hard line break at column 80 only fights that and makes every later edit produce a reflow diff instead of a content diff. Applies to this file, `README.md`, and anything else Markdown. Hard breaks stay meaningful where they are semantic: separate lines for list items, table rows, and code blocks.

## Architectural invariants — breaking any of these breaks the design

1. **Step matching needs no variable values.** `Registry::find` runs on RAW step text. Interpolation happens AFTER `find`, BEFORE `dispatch`, and ONLY on captured args / docstrings / table cells — never on whole step text. This is what lets `validate::check` verify every step before the first request. If you ever need a variable's value to match a step, you have broken the design — stop.
2. **State scoping is asymmetric.** Variables (`VarStack`) live per feature-FILE and persist across scenarios within it. HTTP state (`HttpState`) resets per SCENARIO (`World::reset_scenario` → `HttpState::reset`), and that reset includes the **current API resource**, which returns to `Apis::default_name()` — a scenario never inherits the API another one switched to. This mirrors Behat/Imbo — confirmed from Imbo source, not guessed. Background steps re-run before every scenario.
3. **`contains` JSON is deliberately loose; `equals` is strict.** contains = object subset + order-independent array containment + extras allowed (Imbo semantics, on purpose). equals = exact keys, element-by-element, same length. Do not "tighten" contains — that's a separate function.
4. **The dispatch match is exhaustive with NO catch-all.** `steps::dispatch` names every `StepId`. The compiler enforces completeness; a `_ =>` arm would silently defeat that when new steps are added. Never add a catch-all.
5. **Uniqueness = run_id + atomic counter.** `<<unique()>>` gives per-run prefix (time+random, sortable, greppable) + a monotonic counter → intra-run uniqueness by construction. Do not draw randomness per-value.
6. **Worker-pool runner over chains, exit codes 0/1/2.** The scheduling unit is a **chain**: files sharing a `@serial(<name>)` tag run one after another, every other file is a chain of one. `runner::build_chains` groups and sorts them by `@priority(<N>)` (higher first, default 0, a file takes the max over its tags); `runner::run_all` spawns `concurrency` tokio tasks, at least one and never more than the chain count, over one shared cursor. Each file is run by a nested `tokio::spawn` the worker awaits immediately — that bounds concurrency to the pool and isolates a panic to one file. `--fail-fast` sets an atomic flag checked at exactly two points: before a worker claims the next chain, and before it starts the next file within a chain it has already claimed. There is no checkpoint between scenarios — a file that has started always runs to completion, so a result is never partial: it stops *starting* work, it never aborts a request in flight or truncates a file mid-run. Exit: 0 all-pass, 1 any scenario failed, 2 anything that failed before the first request (validation, config, resource construction, a malformed scheduling tag). Failure ALWAYS dumps the full HTTP exchange, and a file's whole output is composed by `report::render_file` and written with a single `print!` so workers cannot interleave.

## Gotchas that cost real debugging

- **`gen` is a reserved keyword in edition 2024.** Never name a variable/field/param `gen`; use `generator`. (`r#gen` compiles but diverges from the codebase — don't.)
- **reqwest 0.13 gates `.form()` behind the `form` feature.** Already enabled. Adding a feature to a pinned crate is allowed; bumping the version is not.
- **gherkin `Table` rows are guaranteed rectangular** ("each row is always the same length as the first row"). Table indexing after checking the header row cannot panic on parsed input.
- **Integration tests that spawn the stub AND block on `Command::output()` need a multi-thread runtime.** Use `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`. Single-threaded starves the spawned server → requests hang to timeout.
- **Two substitution syntaxes, different phases:** `<placeholder>` = Scenario Outline, substituted at parse time in `feature::substitute`. `<<variable>>` = runtime, substituted in `vars::interpolate`. `substitute` MUST leave `<<...>>` intact (a naive `replace("<key>",…)` corrupts `<<key>>` — it uses a single-pass regex `<<(\w+)>>|<(\w+)>` to protect double brackets).
- **On transport failure (`connection refused`/timeout), `HttpState::send` clears `self.last` first** so the failure dump never shows a stale prior exchange.
- **DB binds are text, the engine coerces.** Every value crosses the wire as text and the SQL carries the type: Postgres binds `$N::type` (type from schema introspection) and casts explicitly, MySQL and MariaDB bind a bare `?` and let the server coerce implicitly. The half that survives both — and the half that matters — is that **Rust never parses the value**. Consequence: a value must be a valid literal for its column type or the server rejects it.
- **The comparison operator is written on the COLUMN, never inferred from the value.** `col: v` is `=`, `col!: v` is `<>`, `col~: v` is `LIKE`, `col!~: v` is `NOT LIKE` — `split_operator` in `db/plan.rs` is the one place those suffixes are read, and an unrecognized one (`price>=`) is an error naming it rather than a lookup for a column with punctuation in its name. The direction matters more than the syntax: an earlier cut chose `LIKE` when the VALUE contained a `%`, which meant a `%` arriving through `<<...>>` from an API response could silently widen a `DELETE` — data deciding the operator is the same class of bug as inferring a config field's type from its text (see the plugin `type` gotcha). An operator anywhere a value is WRITTEN (`I have`, the SET of `I update`) is refused by `plain_column`, because reporting a missing column `slug~` sends the author to their DDL over a typo in their step. Under `~`/`!~` the value is an SQL LIKE pattern in full — `%` and `_` both match, `\%` and `\_` are the literals, backslash being the default LIKE escape on all three engines (so no `ESCAPE` clause is built; MySQL/MariaDB under `NO_BACKSLASH_ESCAPES` are the exception, where those escapes are gone). The COLUMN side goes through `cast_text` and the value binds as text (`(col)::text LIKE $1::text`, `CAST(col AS CHAR) LIKE ?`), so a non-text column matches its own text rendering rather than erroring on the operator — at the cost of the index, the right trade for a cleanup step and the wrong one for a hot path. `<<null>>` is `IS NULL` under `:` and `IS NOT NULL` under `!:`; under a LIKE it is refused, since it could only ever match nothing. What is NOT refused, and is the trap a tester meets in production: a negation carrying a VALUE never matches a NULL column — `name!: keeper` is `name <> 'keeper'`, unknown rather than true where `name` is NULL, so a cleanup written as "everything that is not X" silently leaves those rows. Ordinary three-valued logic, correctly built; documented in `README.md` because it is not what the English sentence meant. Two further ceilings ride along with `cast_text`: the comparison is against the ENGINE'S OWN text rendering, so a pattern over a timestamp is as engine-specific as `I extract` is (same gotcha, same cause), and `LIKE` folds case on MySQL/MariaDB's default `..._ci` collation where Postgres never does. And the friendly "unknown operator" error covers a trailing `!~<>=` only — `slug*:` still reports a missing column, which is the right answer for a character no operator will ever start with.
- **`<<null>>` is the only way to write a SQL NULL.** It interpolates to `vars::NULL_SENTINEL` (`\u{0}__bddkit_null__\u{0}`, NUL-bytes can't occur in `.feature` text), which the DB layer maps to SQL NULL on bind. A literal empty string `""` binds as `''`, not NULL.
- **The DB read path is blob-tolerant on purpose.** `information_schema.DATA_TYPE` arrives as a blob on MySQL 8, and an unwidened `CAST(x AS CHAR)` over a `TEXT` column does the same on MariaDB; `sqlx::Any` refuses to decode a blob into `String`. Every value therefore enters the host through `db::text_col`, which falls back to `Vec<u8>` + `from_utf8`. The obvious "fix" — a width on the cast, `CAST(x AS CHAR(255))` — decodes cleanly and trades the loud decode failure for a silent truncation. Do not add one.
- **`has_default` folds in two engine quirks, both confirmed against live servers.** MariaDB stores the literal four-character string `'NULL'` in `COLUMN_DEFAULT` for a nullable column with no default, where MySQL stores a real SQL NULL — hence the `COLUMN_DEFAULT <> 'NULL'` term. And a `STORED GENERATED` column must report a default so `build_insert` skips it, which is what Postgres's `atthasdef` already does — hence the `EXTRA LIKE '%GENERATED'` term. Neither is decoration.
- **The auto-increment id comes off the INSERT's own result packet** (`AnyQueryResult::last_insert_id()`), never a follow-up `SELECT LAST_INSERT_ID()`. That function is session state, and the pool hands the next statement whatever connection is free — at the default `concurrency` of 8 it returns another file's id, intermittently and with a plausible-looking value. The id is also filtered to `> 0`: sqlx-mysql's OK packet carries `0`, not `None`, when nothing was generated.
- **What `I extract` yields is the engine's own text rendering.** The step is portable; its value is not. `now()` reads back as `2026-08-29 15:11:50.884052+00` on Postgres and `2026-08-29 15:11:50` on MySQL/MariaDB, a boolean as `true` vs `1`, a bare `numeric` as `0` where `decimal(12,2)` is `0.00`. So `I extract` + `should be equal to` is engine-neutral over `varchar`-ish columns and nowhere else. A WHERE against the same column is unaffected — the engine coerces the bind back into its own type.
- **`wants_client_uuid` in the MySQL platform is a heuristic, and is named as one.** Postgres and MariaDB have a real `uuid` type to match on; MySQL does not, so the platform also matches `char(36)`/`varchar(36)` — on BOTH statics, MariaDB included — and a PK of that shape with no value, no default and no auto-increment is filled with a client-side UUIDv7. A `char(36)` PK holding something that is not a UUID gets one anyway. `binary(16)` is refused rather than guessed at (`check_bindable`).
- **DB tests run the compiled binary as a subprocess and need a live database.** `docker compose up -d` first, then run single-threaded (`--test-threads=1`) — the fixture schema `apibdd_it` is shared, so parallel tests race. `BDDKIT_TEST_ENGINE` picks the engine (`postgres` default, `mysql`, `mariadb`) and with it the DSN variable (`BDDKIT_TEST_DSN` / `BDDKIT_TEST_MYSQL_DSN` / `BDDKIT_TEST_MARIADB_DSN`); `tests/db_engines.rs` and `tests/db_mysql_insert.rs` read those variables directly and **skip** an engine whose variable is unset, so they pass by testing nothing unless you export them. Set `BDDKIT_TEST_TIMINGS=1` and pass `--nocapture` to print a per-test timing table. `cargo test --bin bddkit` has no DB dependency and stays fast.
- **`@serial(<name>)` orders files, it does not share their state.** `World` (and its `VarStack`) is built per file inside `run_file`, so variables do NOT flow between files of a chain. This is the natural misreading of the tag — a tester who expects `companyId` to survive into the next file gets an «undefined variable» error.
- **`I delete all "T"` is a full table wipe and does not know about other workers.** Under `concurrency > 1` it removes rows a parallel file is using. Same for any `I have` / `I delete … where` on fixed literals instead of `<<unique()>>`. Isolation in this tool is by data uniqueness, never by transaction rollback — parallelism does not change that rule, it just makes breaking it visible. Put such files in one `@serial(<name>)` chain, or make their data unique.
- **Debug output is not part of the atomic per-file dump.** `I am in debug mode`, `Show …`, and `Print response …` write to **stderr** as they run, so with `concurrency > 1` two workers' debug output interleaves. Deliberate — routing every debug line through a per-file buffer would delay it past the step that produced it. Set `concurrency: 1` while debugging.
- **`--fail-fast` makes a run non-reproducible.** Which files got done depends on timing. That is inherent to «stop starting new work», not a defect.
- **`tokio::spawn` needs `Send + 'static`.** `execute_step` returns `Pin<Box<dyn Future + Send + 'a>>`; keep the `+ Send`. If a new step breaks it, the compiler names the value held across the `await` — scope the guard in a block. Do NOT reach for `tokio::sync::Mutex`: an async mutex held across a DB round-trip serialises the workers, which defeats the whole runner design.
- **`Config.concurrency` defaults to 8.** A suite written for a sequential runner runs 8-way parallel with no config change; set `concurrency: 1` to get the sequential behavior back until the suite is made parallel-safe.
- **SRP `hex-string` pads the client proof before hashing it into the server proof.** (`M1`/`M2` below are the SRP-6a proof messages, nothing to do with any release numbering.) The variant zero-pads the client proof `M1` to the hash's digest width before it goes into the server proof `M2`; getting that padding wrong — e.g. stripping the proof's leading zero the way some browser SRP clients do — silently produces a different `M2` about 1 login in 16, whenever the client proof's leading nibble happens to be zero.
- **Only JSON strings cross the plugin boundary — never a Rust type, never a borrowed slice.** `rustc` has no stable ABI: a `&str` or a `Vec<T>` handed to a `cdylib` built by another compiler is undefined behaviour with no diagnostic. The contract is `*mut c_char` plus the schema in `docs/plugin-authoring.md`. Adding a "just one small struct" fast path is how that becomes a heisenbug in someone else's CI.
- **`Library`'s field order is load-bearing.** Rust drops fields in declaration order, and every function pointer in the struct points into `_library`'s mapping. `_library` is declared LAST so it is unloaded last; moving it up frees the mapping while the pointers beside it are still live. The leading underscore is the whole documentation of the field: it is never read, it exists to be dropped last.
- **A plugin instance handle is a `u64`, not a pointer.** It indexes the plugin's own table, so it is `Send + Sync` for free and can never dangle into a use-after-free on the host side — a stale or forged handle is data the plugin answers `{"status":"fatal","error":"unknown handle"}` to. The mutexes in `Plugins` protect its maps, not the handle. Do not "optimise" it back into an opaque pointer.
- **Plugin steps never become `StepId` variants.** They are `StepTarget::Plugin { lib, step, assertion }` — indices into `Plugins::steps()` — resolved at run time from `list_steps`, so invariant 4 (exhaustive dispatch, no catch-all) is untouched by them. The one plugin-related `StepId` is `UsePluginInstance`, the group-switch built-in.
- **`I use "<name>" <group>` is BUILT at startup from the loaded group names**, as `^I use "([^"]*)" (g1|g2)$` in `Registry::add_use_group_step`. It is not a static entry in `BUILTIN_STEPS`, because `regex` has no lookahead and so cannot express "any word except api/connection" — an alternation over the real names is the only way it cannot overlap `I use "<name>" api` or `I use "<conn>" connection`. Consequence: with no plugin loaded the step does not exist at all.
- **A plugin must never print to stdout, and the host cannot stop it.** A file's whole output is composed by `report::render_file` and written with one `print!` (invariant 6); a plugin's line lands inside another worker's failure dump. Evidence comes back as `diagnostics` in the dispatch reply — and only on the failure path, `passed` drops them.
- **Plugin libraries are deliberately leaked at exit.** `load_plugins` does `std::mem::forget(plugins.clone())` so the mapping outlives every exit path — an early `?`, `process::exit(2)`, the happy path. Running a thread-local destructor or an `atexit` handler after `dlclose` executes an unmapped page; the process is exiting anyway. That leaks the MAPPING only — instances are still dropped through FFI: a `per_worker` one when its file ends, and everything still registered by `Plugins::shutdown` after the pool drains, the call site `tests/plugin.rs::shutdown_drops_the_instance_even_after_a_failed_run` pins.
- **`<<null>>` reaches a plugin as two literal NUL bytes inside a `String`.** `serde_json` escapes them to `\u0000` on the wire, so the host's own `CString::new(request)` is fine — but after the plugin's parse the argument holds real NULs and `CString::new(arg)` returns `NulError`. The fixture's `out` helper shows the fallback. The host side is pinned by `tests/plugin.rs::a_null_sentinel_argument_crosses_the_boundary_intact`; the plugin side is still every author's own to get right.
- **A `per_worker` plugin gets one instance per FEATURE FILE, not per worker.** The manifest value states what the plugin cannot tolerate — one handle called from two workers at once — and per-file satisfies that strictly, because a file is one `run_file` task on one worker and its scenarios are sequential. It is also the grain of everything else a file owns: `World`, its `VarStack` and the per-group instance selection are all per file, so the handle lives in `World` (`PluginState::owned`), the instance is created lazily on the file's first plugin step and is dropped through FFI when the file ends. Widening it to one per worker later changes no ABI and no manifest — which is why no plugin may depend on an instance outliving the file that created it. `shared` is untouched: one lazily built instance in `Plugins::shared` for the whole run.
- **The per-scenario reset is not a broadcast, and must not become one again.** `run_file` hands `Plugins::reset_instances` exactly `world.plugins.to_reset()` — the instances its OWN file has touched — so a file with no plugin steps passes an empty list and makes no FFI call at all. The old `Plugins::reset_scenario` walked every live instance instead: one worker's scenario boundary cleared state another worker was mid-scenario in, and a failed reset was blamed on whichever file reached a boundary first, including files that had never run a plugin step. A loop over the registry «because it is simpler» reintroduces both.
- **Every handle is registered with `Plugins`, even the ones a file owns.** `Plugins::registry` is keyed by `(library index, handle)` — a handle is unique within one plugin, never across two — and every successful `init_instance` inserts there, per-file and shared alike. A panicking file loses its `World` and the handles in `owned` with it, so the registry is the only thing left for `Plugins::shutdown` to sweep after the pool drains; a per-file handle kept in `World` alone would leak a plugin's external process on exactly the path that most needs the guarantee. Know that this one path is reasoned, not pinned: no test panics a file that owns a `per_worker` instance, because the fixture's `catch_unwind` guard means a plugin cannot panic the host and there is no host-side injection point. `shutdown_sweeps_what_a_file_never_dropped` covers the sweep, not the panic that motivates it.
- **`builtin_patterns` must strip group names before tokenizing, and it fails SILENTLY if it doesn't.** It recognizes `([^"]*)`, `(\d+)` and the method alternation by literal text; an unrecognized construct is not an error, it degrades into literal characters. So a named `(?P<path>[^"]*)` left unnormalized does not break the macro-conflict check loudly — it just stops seeing conflicts where the BUILTIN's capture is the side that has to expand, and a macro `I request "/ping"` silently shadows the builtin. `GROUP_NAME.replace_all` at the top of the function is what keeps the token stream identical to the pre-naming one; `a_macro_conflicting_with_a_named_builtin_is_still_rejected` pins it, and is deliberately parameterless (a `{param}` becomes a wildcard that swallows unrecognized literals and would pass either way).
- **`doctor` is not a second validator, and its exit codes are not `run`'s.** Every static stage is a function `run` itself calls, in `run`'s own order; a check `doctor` performs and `run` does not is a bug in `doctor`, so a new rule goes in the **shared** path — the zero `timeout_secs` refusal lives in `http::ApiResource::new`, and every declared SRP resource (not only the default) is validated in `run` itself, both so `doctor` cannot be the stricter of the two. The pair `tests/acceptance.rs::run_refuses_a_malformed_srp_resource_that_is_not_the_default` and `http::tests::a_zero_timeout_is_refused_when_the_resource_is_built` is what keeps that honest. And `doctor` exits **0 or 1 only** — never 2. An unparseable config is the most ordinary thing it has to report, not a reason to answer in a different currency; a script's rule stays "0 = clean, 1 = something to fix".
- **`doctor`'s stage list is not `validate::check` plus resources — it must reach every pre-run check `run` makes.** Three were missed on the first pass and each was a green `doctor` in front of a `run` that exits 2: `runner::build_chains` (a malformed `@priority`/`@serial`), the empty selection, and — subtlest — a DSN whose *scheme* is fine but whose URL the driver cannot parse, since `AnyPoolOptions::connect` parses the whole thing before opening anything (hence the `AnyConnectOptions::from_str` in `db::check_dsn`). When a new pre-first-request check is added to `run`, walk `run()` end to end and add it here too. `doctor::check_features` loads the feature files once and reports two stages from them; scheduling and the parse errors are reported even when the step vocabulary is skipped, because neither depends on it.
- **A bare `doctor` opens no socket of its own, and that is the promise the command is sold on.** `--live` is the only thing the host probes with, `tests/acceptance.rs::doctor_without_live_leaves_an_unreachable_base_url_alone` pins it, and every static stage must stay callable on a train. The one caveat is not the host's: the plugin stage runs `lib.validate_config` through FFI per declared instance (`plugin/mod.rs`), and what third-party code does there is its own business. The live DB probe calls `db::Db::connect` with a ONE-ENTRY map per connection — not to name the dead DSN, which `Db::connect` already does, but because the whole-map call returns at the FIRST failure and a second dead connection would never be probed; `#[derive(Clone)]` on `config::Connection` exists for that. Under `--live` an API answering 404 or 500 is `ok`: reachability is the question, the application's own routing is not.
- **The host's resource field tables are hand-written, and one drift direction is deliberately uncovered.** `API_FIELDS` / `DB_FIELDS` / `SRP_FIELDS` in `config.rs` describe `ApiConfig` / `Connection` / `SrpConfig` for `bddkit resource fields`; Rust has no reflection to derive them. `config::tests::check_table` catches a renamed field and a flipped `required` (for every field the table calls required, a document omitting it must fail to deserialize; the whole document must succeed), and does NOT catch a field added to the struct and forgotten in the table — the benign direction, where the key still works and is only undocumented. Add the entry when you add the field.
- **A plugin's `fields` may only describe groups its own manifest claims** (`library::check_field_groups`), for the same reason a step may not sit in an unclaimed group: the description would shadow the one belonging to whichever plugin owns that group. Reported at load, exit 2.
- **An `implicit_instance` is synthesized into `Plugins::declared` at load, and nowhere else knows it exists.** For a group the manifest lists under `implicit_instance` and the config has no `resources.<group>` section for (an empty map counts as a section), `Plugins::load` inserts an `InstanceSpec` named `default` with the manifest's body and the GLOBAL options — which is why `load` takes `&Options` — and sets it as the group default right there. `doctor`, `probe_config`, `use_instance`, `resource add` all read `declared`, so they treat it as declared for free; `PluginState::current` never learns the difference. Two consequences: `Plugins::add_defaults` EXTENDS rather than replaces, because `main::load_plugins` resolves defaults over the config's groups and never sees the implicit one; and the validation loop runs over `declared.values()`, not the config's instances, with the error labelled `plugin "<name>": implicit_instance.<group>` since there is no `resources.<group>` line to point at. Fixtures: echo declares `{"prefix": "implicit-"}`, worker declares `{}`; the rejection path is reached through `BDDKIT_WORKER_FIXTURE_REJECT_CONFIG`, set on the CHILD by the test (`Command::env`) — the one env switch in a fixture, deliberate, because a manifest body is fixed and no config can make a plugin refuse it.
- **A plugin field's `type` states the FORM of a value, and adds no rule about it.** `ConfigField.value_type` is `string`/`boolean`/`number`/`nonscalar`, absent meaning `string`, and `config::Scalar::from_declared` is the only place those names are mapped. It exists because a flag's value is text and the host writes the YAML: without it `--path_style false` writes `'false'`, which the plugin's own `validate_config` then refuses on every input, forever. That is why an unknown name is refused at load (`library::check_field_types`) rather than read as a string — the silent fallback IS the bug. It is not the JSON Schema #17 refused: nothing here says which values are acceptable, and `validate_config` stays the last word. Never infer the type from the value's text — a bucket may be named `true`, which is the `--set`/`--set-string` split Helm had to grow.
- **`Plugins::probe_config` returns `None` for "the plugin exports no probe", and that is never a failure.** `reset_scenario` can answer `Ok` when its symbol is absent, because "no per-scenario state to clear" genuinely is success; a reachability check that never ran has proved nothing, so `doctor --live` prints it `skipped`. Every host-side problem (unserved group, undeclared instance, malformed reply) comes back as `Some(Err(_))` — to the caller they are all "this instance could not be probed".
- **`resource add` never rewrites a line, and that is the whole reason comments survive.** The block is spliced in after an anchor line — the `<group>:` line, or `resources:` when the group is new — and the spliced text is then re-parsed and compared as a `Value` against the original plus the new resource; anything but equality writes nothing and exits 1. So an existing resource is refused rather than replaced, and the splice works on byte offsets rather than `str::lines`, which drops a trailing newline and hides `\r\n`. The temptation to "just rewrite the block" is how a suite loses the comments inside it.
- **`resources.<group>` bodies cannot contain a YAML tag.** The groups map is `#[serde(flatten)]`, and serde's buffering for flattened fields cannot represent `key: !Foo bar` — it fails with "untagged and internally tagged enums do not support enum input", which does not obviously mean "you used a tag". Anchors and aliases are fine. `api`, `db`, `srp` and `connection` are refused as group names outright (`HOST_GROUPS`).

## Module map (`src/`)

`main.rs` CLI (`run` / `steps list` / `doctor` / `resource fields` / `resource add` / `version`)+orchestration+`build_registry` (the one startup piece `run` and `doctor` share) · `doctor.rs` the pre-run report: stage table, `Status`, human render and `--json` · `resource.rs` `resource fields`: the host's own field tables plus what each plugin says about its groups, rendered and as `--json`; `resource add`: assembles a validated body from `--json`/`--<field>` flags, splices it into the config as text so surrounding comments survive, and writes only after the prospective file re-parses and (unless `--no-check`) probes clean · `config.rs` YAML+${ENV}+resources+`app_env_for` · `options.rs` global/resource polling-option inheritance · `polling.rs` one-shot assertion polling adapter · `unique.rs` run_id/counter · `vars.rs` VarStack+interpolate (holds `NULL_SENTINEL`) · `http.rs` Apis/ApiResource+request state+Exchange · `hawk.rs` Hawk request signing · `world.rs` per-file state · `feature.rs` discover+parse+outline expansion+`TagFilter`+priority_of/serial_of (scheduling tags) · `macros.rs` YAML domain steps · `steps/` registry(`mod.rs`)+api/assert/vars/db/debug/markup/srp/plugin step fns+dispatch+`help`(pattern→template deriver, `locales/steps.<code>.yaml` overlays, `steps list` rows and rendering) · `db/` `reference`(`[connection:][schema.]table` refs)+`value`(one-liner/table pair parsing)+`plan`(INSERT/UPDATE/WHERE/EXISTS SQL builders)+`platform`(the `Platform` trait — every engine-specific difference, and the only place one is allowed to live — with `postgres` and `mysql`; one `MySql` struct backs both the `MYSQL` and `MARIADB` statics, told apart by capability flags, not by a second type)+`introspect`(schema→`TableSchema`)+`ops`(execute+set result vars)+`mod`(connections/`DbHandle`, the DSN-scheme → `Platform` choice, and `text_col`, the one blob-tolerant read boundary) · `json/` path reader + matcher · `srp/` SRP-6a verifier generation and proof computation (`hex_string`, `rfc5054`) · `plugin/` third-party `cdylib` step libraries: `abi`(every serde type that crosses FFI + `ABI_VERSION`, no I/O, no `unsafe`)+`library`(the ONLY `unsafe` module: `libloading`, symbol binding, version check, `String -> String` calls, `free_string` discipline)+`lock`(`.bddkit/plugins.yaml`, project over user)+`mod`(`Plugins`: group→library, declared instances, the lazily filled `shared` instance map and the `(lib index, handle)` registry of EVERY live instance, each behind its own `Mutex`, `call_step`, `reset_instances`, `drop_instances`, `shutdown`; plus `PluginState`, the per-scenario current instance per group and the per-file handles the file has used and the subset it owns) · `validate.rs` pre-run static check · `runner.rs` RunContext (per-run shared state) + build_chains (@serial/@priority) + run_all (worker pool) + run_file · `report.rs` console+exit code.

## Resources and selection

APIs, databases and SRP configurations are global named resources (`resources.api` / `resources.db` / `resources.srp`, plus optional `default_api` / `default_db` / `default_srp`, inferred when a kind has exactly one resource). Any scenario reaches any of them by name — `I use "<name>" api`, `I use "<conn>" connection`. One `reqwest::Client` per API resource, built once into an `Arc<Apis>`; one `sqlx::Any` pool per DB connection for the whole run (`Db::connect`), each carrying the `&'static dyn Platform` its DSN scheme selects — plus, for the `mysql://` family, one `SELECT VERSION()` per connection to tell MySQL from MariaDB.

Any other `resources.<group>` key is a **plugin group**: the host keeps the body verbatim (minus the reserved `options` key), a loaded `cdylib` validates and serves it, and `default_<group>` follows the same inference rule. Selection is `I use "<name>" <group>` and resets per scenario like the API does. Plugins come from `.bddkit/plugins.yaml` (machine state, never committed with the suite); the whole authoring contract is `docs/plugin-authoring.md` and the worked example is `tests/fixtures/echo-plugin`.

Test selection lives on the CLI: a positional path argument overrides `cfg.paths`, and a repeatable `--tag` filters scenarios (feature-level tags are merged onto every scenario at load; an empty selection exits 2).

**Known gap, deliberate:** `resources.srp` accepts multiple named SRP resources, but only the default one is reachable — no step exists yet to select a non-default one by name.

## Macros (declarative domain steps)

YAML files listed under `macro_paths` declare domain steps (`I login as user "..."`) without a rebuild. Matching is transparent — a step is a built-in or a macro, the caller can't tell. Macros take scalar parameters, run in isolated frames that publish results through named/glob `exports`, and may nest up to depth 16. Conflicts and cycles are caught at startup validation (exit 2). Macro call tables/docstrings and loops are intentionally out of scope.

## Eventual assertions

`I expect the next assertion to pass ...` arms exactly one future assertion: inputs are interpolated once, a later modifier silently replaces an earlier one, and an unconsumed modifier is discarded at scenario end or reset. DB attempts query the current connection anew; an HTTP response assertion first checks the saved exchange, then replays its immutable original request at its original API after each mismatch, freshly signing Hawk on every replay. Polling options are inherited global → resource (`options.rs`).

## Adding a built-in step

1. Add a `StepId` variant + its entry to `BUILTIN_STEPS` in `steps/mod.rs`: group, regex, one-line English description. Anchor the pattern with `^…$` and NAME every capture group (`(?P<path>[^"]*)`) — the name is what `bddkit steps list` prints as `<path>`. Keep the ambiguity test green — if two patterns overlap, fix the PATTERN, not the table order.
2. Write the step fn in `steps/{api,assert,vars,db,debug,srp}.rs`.
3. Add a dispatch arm (compiler forces this — no catch-all).
4. Optionally translate the description in `locales/steps.{ru,lv}.yaml`, keyed by the `StepId` variant name. Skipping this is fine — an untranslated step falls back to English per step.

Verb convention: `I <action>` mutates, `should` asserts, `the … is` sets a request param. No verb does both directions.

## Database layer

DB steps live in `steps/db.rs`; SQL is built in `db/plan.rs`, dialected in `db/platform/` and run in `db/ops.rs`. The connection a scenario starts on comes from `default_db` (or is the single declared connection). Table refs are `[connection:][schema.]table` — on Postgres an unqualified name resolves through `search_path`, on MySQL/MariaDB through the DSN's own database, and there the qualifier is a *database* name. Full Gherkin vocabulary (all in `BUILTIN_STEPS`):

- **Insert** — `I have "<table>" with "<pairs>"` (one-liner) · `I have "<table>" where:` (data table, columns as header) · `I have:` (multi-table wide form, first column = table). Schema introspection drives PK/NOT-NULL fill: value given → use it; identity/serial/`AUTO_INCREMENT` or column with a default → omit from INSERT, let the engine generate; no-default `uuid` PK (or `char(36)` on MySQL) → UUIDv7 client-side; NOT-NULL timestamp with no value → `now()`; otherwise fail naming the column.
- **Update** — `I update "<table>" with "<pairs>" where "<cond>"`.
- **Delete** — `I delete "<table>" where "<cond>"` · `I delete all "<table>"` (no WHERE, full wipe).
- **Read into a var** — `I extract "<column>" from "<table>" with "<where>" as "<var>"`.
- **Assert row presence** — `I should have "<table>" with "<pairs>"` / `with:` · `I should not have "<table>" with "<pairs>"` / `with:`.
- **Routines / sequences** — `I call procedure "<name>" with "<args>"` · `I call function "<name>" with "<args>" as "<var>"` · `I get next value of sequence "<name>" as "<var>"`.
- **Connection / debug** — `I use "<conn>" connection` (its API counterpart is `I use "<name>" api`, a `steps/api.rs` step: it switches the target API resource, replaces the headers with that resource's `default_headers`, clears the pending query/body/form, and deliberately KEEPS `last`) · `I am in debug mode` / `I am not in debug mode` (debug prints the generated SQL + binds).

`<pairs>`/`<cond>`/`<where>` are one-liners: comma-separated `col: value`; a literal comma inside a value is escaped `\,`. In a CONDITION the column may carry an operator suffix — `col!:` (`<>`), `col~:` (`LIKE`), `col!~:` (`NOT LIKE`), plain `col:` being `=`; the same column may appear twice, so a range is `amount>=: …` shaped as two pairs once ordering operators exist. Where a value is WRITTEN — `I have`, the SET of `I update` — a suffix is an error, not a column name. `<<...>>` is runtime variable interpolation (`vars::interpolate`), and `<<null>>` yields a SQL NULL (see Gotchas). In a WHERE, a NULL value compiles to `col IS NULL` (`col!:` → `IS NOT NULL`, no bind either way).

**Result variables** written back after a step (readable as `<<...>>`):
- `last_insert_*` — PK values from the last insert: `last_insert_id_<table>` for a single-column `id` PK, `last_insert_<table>_<col>` per column for other/composite PKs, plus a `_<index>` suffix in multi-row/`I have:` inserts.
- `updated_<table>` — rows affected by the last update on that table.
- `deleted_<table>` — rows affected by the last delete on that table.

**Known ceilings / limitations (intentional, not bugs — do NOT "fix" without a spec change):**
- **`I extract` cannot distinguish SQL NULL from empty string.** It runs `SELECT <cast_text(col)> … LIMIT 1` — `(col)::text` on Postgres, `CAST(col AS CHAR)` on MySQL/MariaDB — and coerces a NULL result to `""` (`unwrap_or_default`). A row that is NULL and a row that is `''` both yield `""` in the variable. The text it does yield is the engine's own (see Gotchas).
- **`I extract` reads only the first matching row** (`LIMIT 1`); the WHERE is not required to be unique and no ordering is imposed.
- **Isolation is by data uniqueness, not transaction rollback.** The service-under-test reads through its own connection and won't see uncommitted rows, so tests can't wrap work in a rollback — they rely on `<<unique()>>`-scoped data instead.
- **A connection is bound to what its DSN names.** On Postgres that is one database and many schemas can share the connection (`schema.table`); a second database needs a second entry in `resources.db`. On MySQL/MariaDB a schema IS a database, so `other_db.table` reaches a second one over the same connection where privileges allow — and `search_path` is refused at startup rather than ignored, because there is no session-level equivalent to ignore it into.
- **Not every step reaches every engine.** MySQL has no sequences (`I get next value of sequence` fails naming the platform) and no `RETURNING`, so a PK filled by a server-side `DEFAULT` that is not `AUTO_INCREMENT` is refused *before* the INSERT runs rather than after it commits; MariaDB has both, from 10.5 — older is refused by nothing and fails on a syntax error from the server. `binary`/`varbinary` columns are refused at any width. `README.md` states the support level and `examples/README.md` carries the per-engine table; keep all three in step.

## Dev workflow

- do not use `superpowers` for simple tasks and non-code changes.
- when changing Rust code, use `rust-best-practices` skill.
- TDD per task: failing test → RED → implement → GREEN → commit. Tests assert real behavior, never mock theater.
- Dependency VERSIONS are frozen (features may be added). Edition 2024, toolchain 1.97 — CI pins the exact version in the workflows (`toolchain: "1.97.1"`), so a new clippy lint in a fresh stable can never redden an unrelated PR. Do NOT pin it with a `rust-toolchain.toml`: on a machine whose `stable` already is that version rustup installs a second copy of the same toolchain and can leave it half-installed.
- `cargo test` (unit + `tests/acceptance.rs` e2e against the axum stub). `cargo clippy --all-targets` must be clean — no warnings. `HttpState::current` carries an `#[allow(dead_code)]` because only tests read it; that is correct, don't delete the method.
- Acceptance gate: never weaken a `.feature` or an assertion to force green. A red feature file means a real bug — fix the code or report it, don't patch the test.
- Load-bearing acceptance tests, each pinning an invariant that is easy to break silently: `one_scenario_can_call_two_different_apis` (resources), `two_feature_files_run_at_the_same_time` + `a_single_worker_cannot_release_the_barrier` + `two_files_in_one_serial_chain_never_run_together` (parallelism and per-file variable isolation, proven by a barrier stub rather than timing), `tests/features/srp_login.feature` (registration + authenticated login end to end).
- Subagent reports have miscounted tests and quoted non-existent text — verify claims against files, don't trust report prose.
