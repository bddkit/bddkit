# Event stream and evidence

Loaded on demand; the root `CLAUDE.md` holds the invariants that apply everywhere.

- **The event stream has ONE writer, is opened ONCE, and nothing follows `run_finished`.** `--events <path>` (or `$BDDKIT_EVENTS`, flag wins, empty = unset, `run` only) is opened by `events::open` right after the report paths are prepared and BEFORE the config is read, and the handle is held until exit — never through `report::prepare`, which closes the file, and a FIFO's reader would see end-of-file before the first event. `events::Events` is a cloneable sender into an unbounded `std::sync::mpsc` channel (an emit never waits and never fails: after the terminator the receiver is gone and a file still in flight must not panic over it); one thread owns the file, assigns `seq`, tallies the totals from the `file_finished` lines it writes and maps the NULL sentinel, and writes a batch when the queue runs dry OR it reaches `BATCH_LIMIT` — under load the queue never runs dry, and an uncapped batch put nothing on disk until the run was over. `Events::finish` sends the terminator and JOINS the writer, from `spawn_blocking`; the writer stops after the first `run_finished`, so a second `finish` adds nothing and returns only once the first is on disk. With `RunContext::claim_end` that is what makes «nothing follows `run_finished`, and its `exit` is what the process returns» hold between the interrupt handler and `run`. The tail of `run` that waits for the writer has the handler's two-signal rule itself, because the handler is already aborted: a first signal only prints «still writing» (the run is over and its code settled, the queued lines are not thrown away), a second exits at once with the first's code — without that, a reader that stopped reading would make the process unkillable but for SIGKILL. Its `Interrupts` is registered before `claim_end`, so no signal falls between the handler and the tail. Per-file state is `events::Trace` in `World`. Every step at every depth goes through `runner::execute_step`, a thin wrapper that emits around `run_step`; the reports still see only the top-level step. A macro body step carries the DEFINITION'S line and its `index` — `ExpandedStep.line` stays the caller's, changing it would change an include-in-macro failure text. `file_finished` is emitted by the WORKER in `run_all`, not by `run_file`, so a panicked file is closed too. No subprocess test can panic a file (no host step panics on input, both fixtures `catch_unwind`), so `runner::tests::a_panicking_file_is_still_closed_in_the_stream` panics `expand_outlines` with a hand-made short `Examples` row. `--evidence` (needs `--events` or `$BDDKIT_EVENTS`, checked in `run`, not by clap's `requires`) adds `vars`, `evidence` and `attempt`: `runner::resolve` matches and interpolates a step BEFORE `step_started` so the event carries the slots from the one pass that built the `Args` (a second `<<unique()>>` pass would report values the step never sent); `HttpState` keeps each exchange only while collecting and `World::flush_evidence` emits them from `execute_step` and inside both polling loops, so the innermost step owns them and a replay's exchange precedes its `attempt`; the db emits from `ops::timed`, after the statement ran. Text over 16 KiB is filtered, written through `Artifacts::write` and referenced by a root-relative path. `Trace` evidence methods all take `&self` and are no-ops without `--evidence`.
- **`Trace` is the one gate for what evidence is written, decided per step when it starts.** `--evidence` sources (`events::Sources`, the ONE parser behind the flag, `$BDDKIT_EVIDENCE` and the config key's serde) make a step live (marked under `marked`, or `all`), deferred (`failures`) or off; `Trace::modes` runs parallel to `open`, so `evidence_on()` — and with it the plugin dispatch's `evidence` key — is the innermost step's mode. `HttpState` keeps every exchange whenever any source is active and `Trace` drops the off ones at flush. The mark (`I am collecting evidence`, the `@evidence` tag) is scenario state reset in `Trace::scenario_started`, the way `reset_scenario` clears debug; it lives in `Trace`, not `VarStack`, which is why an include's stack swap does not hide it. Deferred events are masked BEFORE they enter the `Held` buffer (they are built by the same emit code) and AGAIN at flush, with the set as it stands then — a value can become a secret after the step that sent it (`deferred_evidence_is_masked_with_the_secrets_known_when_it_is_written`). Long text is held in memory with its artifact path pre-allocated, so the event's reference is final and a passing scenario writes nothing; the per-file cap (`$BDDKIT_EVIDENCE_BUFFER`, default 64 MiB, parsed only when a source is active) bounds that long text and nothing else — held events are not counted (a `ponytail:` at `Held`). A held event's `t` is its flush time: `Tally::encode` clamps `t` to rise in `seq` order, so stamping it earlier would change nothing. `scenario_finished` flushes only for a failure AND `!RunContext::interrupted()` — not `stopped()`, which `--fail-fast` also sets: after a signal the handler's `Plugins::shutdown` can fail a plugin step still in flight, and that scenario was stopped, not failed (`a_scenario_that_fails_after_an_interrupt_drops_its_deferred_evidence`).
