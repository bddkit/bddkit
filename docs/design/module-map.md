# Module map (`src/`)

The full per-module description that used to live in `CLAUDE.md`. The root file keeps a one-line-per-area map; this is the detail.

`failure.rs` `FailureKind` and `StepError`, the class of a failure and the error every step returns · `privacy.rs` what counts as a secret and the filter that hides it: the name rules (`variable_is_sensitive`, `field_is_sensitive`), `Secrets` (the value set; `mask` merges overlapping matches into one `***`), `Redactor` (one file's shared handle on it: vocabulary, set, `register`/`mask`/`mask_json`, `fork`), the layered options (`PrivacyLayer` → `Privacy::resolve`, flag > env > config > default, `*_only` resets and the other form appends), the JSON/form/query scanners (`json_hits`, `pair_hits`, `query_hits`, `mask_ranges`), the config walk (`secrets_in`) and the process-wide sink `main` and `config::load_str` write into (`set_flags`, `record`, `mask_text`) · `main.rs` CLI (`run` / `init` / `steps list` / `doctor` / `resource fields` / `resource add` / `plugin` / `upgrade` / `version`)+orchestration+`build_registry` (the one startup piece `run` and `doctor` share)+`config_dir` (the `--config`-relative anchor `load_plugins` and `doctor::check` both walk up from) · `upgrade.rs` `bddkit upgrade`: receipt check, staging, plan, switch, rollback (the plugin half reuses `plugin/manage.rs`'s `fetch_into`) · `init.rs` `bddkit init`: `InitArgs` (the flags), `Answers`, `from_flags` (the non-interactive path and its refusals), `ask` (the only `dialoguer` code besides `telemetry::ask_yes_no`), `apply` (writes the config, the example feature and `.gitignore`, installs through `plugin::manage::Context::install`, prints the `resource add` hints, ends with `doctor::check`) · `telemetry.rs` anonymous usage counts: the decision (`decide`, `Sources`, `Decision`, `ConfigKey`, `config_key`), the CI detection (`ci`, also behind `report::progress::interactive`), the endpoint rule, the answer files (`layer_answers`, `answer_path`, `store_answer`), the yes/no prompt (`ask_yes_no`, `ask_line`, `parse_line`) and `should_ask`; `telemetry/payload.rs` the closed payload struct and its enums; `counters.rs` leaf steps per group and outline rows; `run.rs` `RunProbe`, what `run` learns as it goes and the payload it assembles; `doctor.rs` the `doctor` row and payload; `end.rs` `end`/`record`, how a command that asks ends; `command.rs` `bddkit telemetry status|show|on|off`, `Setting::discover` and `record_if_on` for the commands that never ask · `doctor.rs` the pre-run report: stage table, `Status`, human render and `--json`; also reports the resolved `.bddkit/` layer chain (`directories` rows, one per candidate file) and which layer each plugin lock entry came from (`plugin_lock` rows) · `resource.rs` `resource fields`: the host's own field tables plus what each plugin says about its groups, rendered and as `--json`; `resource add`: assembles a validated body from `--json`/`--<field>` flags, splices it into the config as text so surrounding comments survive, and writes only after the prospective file re-parses and (unless `--no-check`) probes clean · `config.rs` YAML+${ENV}+resources+`app_env_for`+`resolve_config_path` (`--config` → `$BDDKIT_CONFIG` → `./bddkit.yaml`/`./bddkit.yml`, shared by `run`/`doctor`/`resource add`/`steps list`/`resource fields`) · `dirs.rs` the `.bddkit/` layer chain (shared/user/project, `--bddkit-dir`/`BDDKIT_DIR` override replaces the whole chain with one directory) and `candidates` (`<stem>.yaml` then `<stem>.local.yaml` per layer, lowest precedence first); also `data_dir` (the layer's library directory, split from its config directory the way FHS/XDG split them) and `install_layer` (the auto-pick rule `plugin install` uses when no `--layer` is given) · `options.rs` global/resource polling-option inheritance · `polling.rs` one-shot assertion polling adapter · `events.rs` the `--events` stream: `open`, `Events` (sender + the one writer thread, `finish`), `Trace` (per-file numbering and the in-flight step stack) · `unique.rs` run_id/counter · `vars.rs` VarStack+interpolate (holds `NULL_SENTINEL`) · `http.rs` Apis/ApiResource+request state+Exchange · `hawk.rs` Hawk request signing · `world.rs` per-file state · `artifacts.rs` the run's evidence root (`--artifacts-dir` / `BDDKIT_ARTIFACTS_DIR`, else `<temp>/bddkit-<run_id>`) and the `<root>/<six-digit counter>` allocator for plugin dispatches: owned by `RunContext`, handed to every `World`, so a run with no plugin can allocate too · `annotate.rs` source-line scanning and registry-based comments/disabled steps/sections · `feature.rs` discover+parse+outline expansion+`TagFilter`+priority_of/serial_of (scheduling tags) · `macros.rs` YAML domain steps · `steps/` registry(`mod.rs`; `Registry` carries each entry's template and a loose regex, and `unknown_step_detail` is the one place the unknown-step explanation is built — a typed parameter's refusal first, else `suggest.rs`' word-level "did you mean")+`expression`(the one parser of builtin and macro declarations: Cucumber Expression + `{name:type}`, parameter types, conflict tokens, templates)+api/assert/vars/db/debug/markup/srp/plugin step fns+dispatch+`help`(deriver of `steps list` templates for plugin step patterns (builtins get theirs from `expression`), `locales/steps.<code>.yaml` overlays, `steps list` rows and rendering) · `db/` `reference`(`[connection:][schema.]table` refs)+`value`(one-liner/table pair parsing)+`plan`(INSERT/UPDATE/WHERE/EXISTS SQL builders)+`platform`(the `Platform` trait — every engine-specific difference, and the only place one is allowed to live — with `postgres` and `mysql`; one `MySql` struct backs both the `MYSQL` and `MARIADB` statics, told apart by capability flags, not by a second type)+`introspect`(schema→`TableSchema`)+`ops`(execute+set result vars)+`mod`(connections/`DbHandle`, the DSN-scheme → `Platform` choice, and `text_col`, the one blob-tolerant read boundary) · `json/` path reader + matcher · `srp/` SRP-6a verifier generation and proof computation (`hex_string`, `rfc5054`) · `plugin/` third-party `cdylib` step libraries: `abi`(every serde type that crosses FFI + `ABI_VERSION`, no I/O, no `unsafe`)+`library`(the ONLY `unsafe` module: `libloading`, symbol binding, version check, `String -> String` calls, `free_string` discipline)+`lock`(reads `plugins.yaml`/`plugins.local.yaml` over the `dirs.rs` layer chain, name-keyed override — a later candidate replaces an earlier entry of the same plugin `name`, and each surviving entry is stamped with the layer it came from)+`install`(the `bddkit plugin` fetch path: index fetch+parse, `name@ver`/`owner/repo@ver` argument parsing, latest-tag resolution via the `releases/latest` redirect, asset naming and host-target selection, sha256 verification, extracting the one dynamic library from a tar.gz/zip)+`manage`(the six `bddkit plugin` commands: install/update/remove/prune/show/list, which lock file and data directory a `--layer`/auto-pick/`--bddkit-dir` resolves to, and `owned` — the exact-shape check that gates what `remove`/`update` may delete)+`mod`(`Plugins`: group→library, declared instances, the lazily filled `shared` instance map and the `(lib index, handle)` registry of EVERY live instance, each behind its own `Mutex`, `call_step`, `reset_instances`, `drop_instances`, `shutdown`; plus `PluginState`, the per-scenario current instance per group and the per-file handles the file has used and the subset it owns) · `validate.rs` pre-run static check · `runner.rs` RunContext (per-run shared state) + build_chains (@serial/@priority) + run_all (worker pool) + run_file · `report/` `mod.rs` console+exit code, plus the JUnit XML and Cucumber JSON writers and `prepare` (create-or-truncate a report path); `model.rs` `bddkit report`'s one pure fold of the event stream into the tree every report renders; `html.rs` that tree as one self-contained page with `viewer.js`/`viewer.css` compiled in; `markdown.rs` that tree as marker-delimited Markdown for agents (`docs/report-markdown.md` is the contract): the body is rendered first and the header twice, once to measure it and once with the index's line ranges shifted by that height, so a range is exact; every content line goes through `guard`, so only bddkit's own markers start with `<!-- bddkit:` at column 0; `embed.rs` `--embed-artifacts`: which linked files go into the page (`plan`: safe relative paths, on-disk size smallest first under `--embed-limit`), their PNG re-encoding to WebP and the parallel, order-independent `encode`; `progress.rs` the stderr line and `interactive()` — the ONE definition of «a person at a terminal» (stderr is a TTY and none of the CI variables of `telemetry::ci` is set and non-empty: `CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `JENKINS_URL`, …) for anything that draws, and `can_prompt()`, the same plus stdin, for anything that asks (`init`, the telemetry question) — reuse them rather than write another; `command.rs` the `report` subcommand (outputs validated before the stream is read, written under temporary names and renamed only when all are complete).
